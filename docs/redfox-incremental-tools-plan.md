## 2. Seedream Lite：停新建，保留历史与恢复

当前 `images.ts:imageOptions()` 同时参与页面模型选项；`image-models.ts`、`imagePairs` 和解析器又负责旧任务恢复。直接删除枚举、模型映射或全部查询入口会破坏历史兼容。

最小调整：在现有图片模型定义中集中表达 Lite 停止新提交的判断，前后端消费同一事实；不建立供应商在线状态中心、定时探测或自动切模型机制。

- 图片生成选择器不再允许选择 Lite；旧草稿清楚提示“该模型已停止新建，请重新选择”，不静默变成 Pro 或其他模型。当前生成与旧任务查询共用模型选项，不能直接从完整 `models` 中删除 Lite：仅过滤生成用途，分别初始化生成表单和查询表单的模型；旧任务查询链接仍传原 Lite 模型，不能回落到默认 GPT-Image-2。
- 后端新建命令同样拒绝 Lite；同一幂等命令重放仍返回原执行记录，不制造第二条任务。模型历史解析、接口 ID 和价格历史保留。
- 旧排队任务尚未实际提交时，阻止新生成，以及为该生成继续发生的新参考图上传；使用现有 `needs_review`／取消流程显示原因，不新增状态。停止新建不能冒充暂时关闭总开关的 `RedfoxDisabledError`，否则现有执行器会每 60 秒重新等待，而不是完成退役收尾。
- 已收到提交响应、业务进度尚未写完时，重放已收回执取回 `taskId`，不把它当作新提交拒绝，也不重新请求生成。
- 已有 `taskId` 的任务保留原查询、结果保存和执行记录；旧任务查询区注明 Lite 仅用于已有任务。查询接口是否仍能工作没有真实验证；调用若报不支持或失败，保留原因并沿用有限恢复规则，不重新生成、不自动换模型。
- 结果未知的生成请求继续走现有人工处理边界，不因为入口停用就释放成可重新提交。已有本地文件照常查看和下载。

实现连接点限于 `providers/redfox/images.ts`、`image-models.ts`、`image-execution.ts` 及图片表单／模型选项。利用现有回执 `call/reuse/unknown` 区别真正外发与本地重放，不改通用回执状态机。新建检查与执行时检查分别覆盖新命令和旧排队任务，属于必要边界，不是两套状态源。

## 3. 知乎：完善已有平台，不另造入口

入口分工如下。四项新能力均可在“数据工具 → 平台查询 → 知乎”手工使用，其中文章详情供现有采集订阅补全正文、评论供现有研究快照订阅定时保存；两种入口共用接口适配与执行记录。

| 能力 | 数据工具 | 信源／采集订阅 |
| --- | --- | --- |
| 关键词搜索（已有） | 手工搜索文章、回答等既有范围 | 原有定时搜索入口继续保留 |
| 文章详情（新增） | 按文章 ID 查询，或从已收文章搜索结果查询详情；需要入库时选择所属信源导入 | 知乎文章搜索订阅可显式开启详情补全，采回的文章使用订阅所属信源，不重复选择 |
| 账号详情（新增） | 查询昵称、简介、粉丝等账号资料 | 本轮不增加独立订阅；账号资料接口不等于账号作品列表，不能承诺自动采集该账号全部文章 |
| 文章评论（新增） | 查看文章评论及显式续页，可带入新采集订阅 | 固定文章 ID，每轮保存评论首页，使用已有评论快照流程；结果和进度在执行记录查看，不自动入库为文章 |
| 搜索热点（新增专用接口） | 查看热搜词、热度及文档提供的热／新标签 | 定时保存继续使用现有“热点研究 → 各平台热点榜”，选择知乎；不把专用接口再接成第二条定时路线，不自动拿热搜词去搜索或生成文章 |

信源负责材料归属和参与权限，采集订阅负责定时配置，数据工具负责手工查询；它们共用接口适配、预算、回执和执行记录。只查询不要求选信源；内容导入才使用已选归属。评论和热点是研究快照订阅，不产生新闻材料，沿现有研究订阅规则不强制选择信源；即使从信源入口进入，也不因此获得文章导入或公开权限。

现有热点定时能力已核实：AgentKey／TikHub 有抖音热点榜、B站热搜词、X 趋势词；微博热搜有 Redfox 和 AgentKey／TikHub 路线。Redfox `S28Q6HUD`“各平台热点榜”支持快手、抖音、小红书、微博、百度、B站、知乎、今日头条，其中 `platform=9` 为知乎，已进入采集订阅白名单。榜单保存为执行记录中的研究快照，不自动导入文章，因此不强制选择材料所属信源。这里只确认代码支持，未启用或真实调用这些订阅。

专用知乎热搜文档无需日期参数，返回标题、热度、热／新标签和排名；已有聚合路线按指定平台和日期范围返回标题、热度、上榜时间及搜索链接，现有订阅每轮按上海时区查询当天。不能据此认定两者是同一份榜单，文档也没有承诺刷新间隔或谁更实时。本轮专用接口仅供手工查询，定时采集只维护已有聚合路线。

### 3.1 查询与文章详情导入

现有 `zhihu-contract.ts`、`zhihu.ts` 只有关键词搜索；`import-zhihu.ts` 的搜索结果导入仍要求核实原文。新详情文档已给出原文、正文和时间契约，可以减少人工填写，但不应把详情能力推广到知乎所有内容类型。

- 在现有知乎操作描述、参数校验和解析分支中补四个接口。沿用同步查询命令、Redfox 传输及执行记录，保持统一的供应商、参数、回执、结果关联。
- 文章详情将请求 `articleId`、返回 `opusId`、`type=article` 和专栏原文地址相互核对；ID 保留字符串。成功但身份冲突、地址缺失或不合法的结果保留诊断，不导入错误作品。
- HTML 正文复用现有正文清洗与材料写入能力；后台不直接执行供应商 HTML。时间按新详情文档的 Unix 秒解析，旧搜索时间仍按自己的契约处理。
- 独立查询无需先选信源；点击导入时才使用结果区的所属信源选择。订阅执行则沿用订阅所属信源，不新增“目标信源”，不要求补齐作者 ID 才能导入。
- 去重、已有关联、修订、当前参与方式、全文权限及后续分析入队复用现有材料管线。拿到正文不意味着允许前台公开全文；不重写旧任务归属，不自动回填历史文章。
- 评论、账号、热点使用现有研究结果组件和 JSON 诊断。评论与热点不能伪装成 `zhihu_work` 来获得导入按钮；空列表仍保存查询摘要，区别于解析失败。
- 评论第一页不填 `nextUrl`；后续只按实际返回的续页地址发给 Redfox，复用现有查询表单进行显式分页，不让服务端直接抓取该地址或自建爬虫。

### 3.2 必须补齐的详情连接点

若只在下拉菜单加“文章详情”，现有搜索和订阅仍无法利用它，不能算此次补齐完成。

- 已收到的知乎搜索结果，只有查询范围明确为 `vertical=article`、作品 ID 存在且来源回执匹配时，才提供现有“查询作品详情”动作；由实际搜索结果的 `opusId` 传入详情 `articleId`。
- 扩展现有 `work-detail-options.ts`、`work-detail-origin.ts` 中的知乎分支，冻结原搜索结果和作品 ID，并在详情响应后再次核对。未筛选的混合搜索、`answer`、`zvide` 不自动套文章接口，不按昵称推断内容类型。
- 在 `collection-detail.ts` 补同一条映射，让现有知乎文章搜索订阅可显式开启详情补全；默认关闭，旧订阅不自动修改。复用 `enrichDetails`、详情次数上限及既有 `redfox.platform.detail` 步骤。
- 详情结果导入复用 `collectedDetailContext` 证明其属于本轮、本页、同一作品，保留原发现时间和所属信源。收响应后中断，恢复时只重放回执并完成入库，不重复收费。
- 账号详情与专用搜索热点不加入定时采集白名单；评论按下节加入已有快照订阅。不扩展供应商切换矩阵，已有知乎搜索和聚合热点订阅不自动改配置。

### 3.3 知乎评论：复用现有定时快照

最小闭环是“数据工具查询文章评论 → 带入新采集订阅／直接新建评论订阅 → 每轮保存首页 → 执行记录查看数量、评论和回执”。使用已有 `redfox.platform.collection → redfox.platform.page`；不另建评论表、任务类型、状态、队列或定时器。

- **范围：**订阅固定一个 `articleId`，每个正常轮次只查询首页一次，不自动跟随 `nextUrl`，不获取回复树，不为其他新文章自动创建评论任务。这是按时留存样本，不承诺全量评论、增量监控或完整历史。
- **参数：**手工查询允许 `nextUrl`，订阅参数只允许 `articleId`。从已翻页查询带入订阅时，仅带入文章 ID，并显示“定时保存每轮从首页开始，不沿用查询续页”；预览、草稿、保存使用同一订阅参数范围。后端拒绝订阅中的 `nextUrl` 以及超出单页范围的配置，不能只靠前端隐藏。
- **运行限制：**页数固定为 1，详情上限为 0，不能启用详情补全或自动保存视频，也不接受详情操作／详情页参数。条目上限复用现有字段，仅限制本地保留的结构化评论数；该接口没有每页条数参数，不承诺上游按此数量返回。新建默认停用、周期和启停方式沿用现有订阅，不增加自动启用或新的轮询策略。
- **归属：**把操作加入现有研究订阅集合，使其无需材料所属信源即可调度；不因缺少作者 ID 转入隔离、不增加“目标信源”。请求文章 ID 保存为查询范围，评论作者字段只代表评论者，不推断为文章作者，也不建立作者信源绑定。评论不能导入为新闻、自动分析或进入前台栏目。
- **结果：**按评论接口分支解析为已有 `social_comment` 研究记录，保留评论 ID、正文、昵称、文档拼写 `avatorUrl`、评论者 `urlToken`、点赞数原值及秒级时间。复用 `query_summary`，保存实际返回的 `nextUrl` 作为分页事实，但令 `nextParameters=null`，不自动抓取该地址。
- **数量与完成：**现有执行器已能保存纯研究结果并结束，但仅加白名单会把有评论的页误记为 `empty-work-page`、已处理数 0。局部补齐快照摘要的实收、选入、处理、截断数及 `snapshot:true`；停止原因用现有 `single-request`／`item-limit`，通过原有 `advance(..., null)` 完成并释放订阅占用。`items:[]` 是有效空快照；缺失／错误结构及供应商失败不能变成空成功。
- **保存与恢复：**摘要、评论及 `sourcePageResultId` 继续在原事务中登记，同一轮恢复不重复保存，下一轮允许再次记录同一评论以保留快照。继续使用既有执行结果保留规则：未关联且符合清理条件的完成／失败结果默认 30 天后到期，不新增永久评论档案或清理任务，页面沿用到期提示。
- **编辑与停用：**沿用订阅版本、旧轮停止及占用释放机制；更改文章 ID 后，旧轮结果仍属于旧执行记录，不写成新文章的快照。关闭订阅后不再创建新轮次；预算等待和故障恢复不绕过既有启停与版本检查。

必要连接点集中在现有文件，不引入通用能力注册框架：

## 5. 商品卡搜索的最小接法与 Facebook 暂缓边界

**商品卡搜索：**已纳入本轮。在既有 AI 搜索模型选项增加“千问（含商品卡）”“豆包（含商品卡）”，复用 `ai-search-contract.ts`、`ai-search.ts`、`ai-search-execution.ts` 的提交／查询／结果流程。保留现有普通千问与豆包的接口和历史输入语义，不悄悄替换。商品卡保存在现有答案结果数据中，增加一个局部列表展示标题、价格原值、店铺和安全链接即可；没有商品卡时仍可展示正常回答，不把可选卡片缺失误判为失败。不新增商品库、购物系统、定时订阅或自动新闻发布。两个变体按实际契约处理状态、引用与商品字段：新接口的 `processing/completed/failed` 不能套用旧豆包的等待状态枚举，千问 `sourceSeq`、豆包 `searchGuid` 也不能冒充旧引用字段。只展示实际返回的关联，关联不明时保留正文与独立商品卡，不猜引用。新接口公开提交基础价为 0.12 元，查询标价为 0 元；使用现有 AI 搜索与轮询预算，估价不当作实扣。

**Facebook：**保留第三阶段候选。最低有用闭环是主页帖子列表＋详情＋可选账号核对＋沿所属信源导入，评论作为只读研究。可以复用平台查询表单、同步执行器、采集订阅和材料管线，但仍需补平台枚举、分页映射、解析器、原文核对、导入和测试，不是只加四个下拉选项。Redfox 与未来 AgentKey 路线各自完成请求和补全；不为身份问题把两家串接。当前详情文档的 `videoUrl=null` 不能证明支持自动下载，不在本次扩展视频保存范围。

## 7. 开发前方案复审结论（历史）

- 架构复用：四项知乎能力接入既有同步查询，文章详情接逐项补全，评论定时保存接已有研究订阅／页面执行步骤／结果组件；商品卡复用 AI 搜索提交／查询执行器和答案数据，无需第二套任务或结果管理。
- 避免重复：不建商品实体、评论表或永久评论档案、Facebook 专用管理页、在线目录同步服务或模型可用性平台；知乎热点定时只有已有聚合路线，账号详情不新增订阅。评论仅固定文章首页，不顺带扩成全量爬取或新增文章监听。
- 必要连接已补入方案：评论的研究分类、订阅专用参数、查询带入／预览、后端单页约束、纯研究摘要与收尾、结果组件说明及 collect 价格缺一不可；只加白名单会出现错误计数或不适用选项，不能当成完整接入。
- 生命周期收尾：Lite 覆盖旧排队上传、生成提交和回执恢复，保留历史兼容；知乎详情保留同作品核对和同源导入，评论沿用事务、回执、版本及结果到期清理，不新增状态归属。
- 不扩大权限：仍以管理员配置的所属信源为权威，作者 ID 仅作溯源；研究结果不自动成为新闻，正文获取不扩大公开权限。
- 本轮复审已将上述必要连接和验收标准写清；未发现需要新增表、状态、队列或通用抽象的理由。剩余边界是尚未进行的真实响应／计费验证，不以文档样例代替联调。本结论是方案评审，不代表代码已实现或测试已通过；不新增额外审批平台或质量门禁。
