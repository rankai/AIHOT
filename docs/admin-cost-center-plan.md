# 后台统一成本中心接入方案

> 状态：首版已实施，经 `kimi-code-cn/k3.1-pro-highspeed` 复审并修复后完成本地验收，2026-10-31；未提交、未推送、未部署。实际结果、性能数据、页面证据和残余风险见[统一成本中心首版本地验收](reviews/2026-10-31-cost-center-acceptance.md)。五项评审意见的采纳方式见第 12 节。
>
> 范围：模型与供应商接口的调用明细、用量和费用统计；预算与费用相关职责中，设置页继续负责次数预算，统计进入成本中心；保留现有任务执行、异常恢复、会员积分报价与结算机制。

## 1. 结论

新增独立的后台 `/admin/costs`，在“系统”导航中显示“成本中心”。首版提供“概览”“调用明细”“已存账单”三个视图，支持按供应商、接口服务、模型、Skill 和用户筛选及分组。

不新建一套供应商调用流水。调用统计继续以 `receipt_attempts` 的外发尝试记录为事实源，在现有 `paidRequest()` 占位事务内补充三类证据：

1. 计费供应商、具体接口和模型各自的身份；
2. 外发时的任务和用户归属，以类型明确的字段记录；
3. 外发时确定的价格快照。

成本中心新增统一只读读模型，复用现有回执、任务、助手激活、用户和万相任务费用证据。除万相等明确的特殊计费外，一条外发尝试最多对应一个本地成本项；万相按生成任务计一次，轮询不重复计费。

首版只做本地已存证据。核心交付是概览与调用明细，“已存账单”复用现有查看能力。保留原回执幂等键、预算服务名和会员计费键；统计用身份通过增量字段补齐。首版不包含自动拉账单、金额熔断、毛利统计或通用分时定价引擎。

## 2. 当前问题与已有基础

### 2.1 已有能力

| 现有能力 | 权威位置 | 本方案如何复用 |
| --- | --- | --- |
| 逻辑请求、原始响应、恢复复用 | `receipts` | 提供 purpose、请求摘要和逻辑请求身份，不把恢复复用算作新外发 |
| 每次外发尝试登记 | `receipt_attempts` | 提供 service、旧 model、origin、状态、usage、cost、币种、费用依据和耗时 |
| 任务、执行者、回执关联 | `operation_runs`、`operation_results` | 提供 run、actor 和已有回执关系；新调用在外发时冻结归属，避免只依赖短期结果关系 |
| 助手用户与回合 | `assistant_sessions`、`assistant_turns` | 提供 session、turn 和真实 owner |
| 助手模型步骤 | `assistant_model_steps` | 通过 receipt 关联具体模型调用 |
| Skill 激活 | `assistant_activations`、`assistant_tool_calls` | 提供版本化 Skill/module 身份及子检索的激活来源 |
| 供应商与模型价格 | `service_prices` | 提供普通输入、缓存输入、输出和按次价格；新增调用保存当时快照 |
| 万相任务费用 | `providers/aliyun/wan-costs.ts` | 复用 taskId、提交回执、输出秒数、价格快照和去重逻辑 |
| 会员积分 | `member_credit_*` | 保持独立账本和现有结算，不拿来冒充供应商成本 |
| 后台预算 | `/admin/settings` | 保持次数预算配置，不扩展成成本页 |
| 模型质量与性能 | `/admin/models` | 保留模型切换、成功率、延迟、tokens 和评测 |
| Redfox 已存账单 | `redfox-costs.ts` 与对应 UI | 账单核对迁入成本中心；本地费用分组由统一读模型接管 |
| 后台 UI | `features/admin/ui.tsx` | 复用页面、卡片、统计、筛选、表格、表单、状态和时间组件 |

### 2.2 当前缺口

- `assistant.text` 是内部服务名，不能直接说明计费供应商。Redfox 将 operationId 存在旧 `model` 中，AgentKey 的计费方与路由上游也不同，必须在统计中分别表达。这些旧字段参与回执身份和价格查询，不能就地改义。
- 模型调用通常有 tokens，但 `cost` 为空；已有模型页按当前价格计算历史费用，调价后结果会变化。
- 助手规范化 usage 当前没有保留 DeepSeek 的缓存命中/未命中 tokens，无法可靠使用缓存价格。
- attempt 没有稳定冻结的 run/user 归属；历史共享回执若关联多个任务，不能随意选一个用户。
- Skill 在模型返回并执行 `load_skill` 后才激活。首轮选择阶段的模型调用不能伪装成已经激活的 Skill。
- 一个回合可激活多个模块，后续步骤可同时拥有多个模块的工具；单给一个步骤挂一个 `activation_id` 不足以表达事实。
- `assistant_tool_calls.activation_id` 已有字段，但当前检索启动路径没有写入它；必须补齐验证后的赋值，不能把“字段存在”当作“归属已记录”。
- 万相按生成任务和输出秒数估算，不能把提交与每次轮询都当成一笔生成费用。
- `origin='live'` 是外发来源标记；attempt 是已登记的外发尝试，可能在占位后中断。两者均不证明生产环境、送达或扣费。

## 3. 目标与非目标

### 3.1 首版目标

1. 管理员能回答：某时段某供应商、服务、模型、Skill 或用户发生了哪些外发调用，状态、用量、耗时和本地登记费用是多少。
2. 汇总和明细使用同一筛选条件、同一时间范围和同一费用口径，可以从分组进入对应明细。
3. 新调用的估算价格不随后续调价变化；历史缺证据的数据明确显示未知。
4. 重试、回执复用、pending/unknown、万相轮询和多 Skill 步骤不被重复或错误计费。
5. 新模型和普通新供应商沿用现有 `paidRequest()`，补齐本方案的身份、归属及用量合同后获得明细和汇总；特殊计费只增加局部证据处理。
6. 迁移现有 Redfox 费用页和模型页的费用职责，避免长期出现三个不同口径。

### 3.2 首版不做

- 不自动轮询供应商账单，不承诺逐笔对账、余额差归因或真实利润。
- 不把次数预算改成金额预算；金额熔断如需增加，另立方案。
- 不改变会员套餐、工具积分价、创作报价、预约、释放或结算。
- 不做任意比例的多 Skill 成本分摊，不用“平均分”制造精确感。
- 不建设 Provider Registry、通用计费规则引擎、BI 平台、图表平台或导出平台。
- 不用当前价静默重算全部历史，不伪造历史用户、Skill、供应商或实收成本。
- 不新增前端或后端框架、数据库、ORM、定时任务和外部依赖。

首版完成标准：当前普通模型、助手模型、Redfox、AgentKey、百炼/万相调用可查；五个核心维度均可筛选并进入明细；有证据的费用能复算、未知项可见；同一统计口径可对上明细；预算、会员扣分与恢复行为通过定向回归。价格配置管理界面、自动账单采集和其他尚未接入服务不作为首版交付前提。

## 4. 页面与操作流程

### 4.1 入口和职责

后台“系统”组在“模型与评测”附近增加“成本中心”，路径 `/admin/costs`。

- **设置**：在预算与费用这一范围内继续负责服务次数上限、总池/会员池/Admin 池，仅增加“查看成本中心”链接。其他既有运营设置保留。
- **模型与评测**：继续负责模型配置、质量、延迟、tokens 和 SelectBench。移除独立的当前价估算逻辑，费用区域改为带模型筛选条件的“查看成本”链接；不把 capability 与成本中心重新映射一套。
- **数据工具**：继续负责查询和生成操作。“费用与账单”入口迁到成本中心；旧 `/admin/data-tools?view=costs` 重定向到 `/admin/costs?view=billing`，避免两个页面同时维护。
- **运行与执行记录**：继续负责异常恢复。成本明细链接到已有运行详情并提供回执身份，不在成本中心增加恢复按钮。

### 4.2 概览

默认查询最近 7 天、`origin=live`、全部执行环境。页面用“已登记调用”表达次数；说明“来源与执行环境不证明供应商实扣”。可切换 replay/imported，执行环境分组展示。开发环境调用官方付费接口仍是开发调用，其实际成本照常记录。

顶部筛选：

- 起止时间：提供最近 24 小时、7 天、30 天及自定义日期；界面标明北京时间，传给 API 的 ISO 时间包含时区。开始含、结束不含，单次范围最多 92 天。
- 计费供应商、接口服务、模型：复用现有 `Select`，较多接口可配一个 `Input` 过滤当前候选；原始 ID 可查看，名称取自既有目录。接口服务按 service 与 operation 细化，模型单独筛选，不将 API 编号显示成模型。
- Skill：按 `skillId + moduleId` 筛选；版本在分组和明细显示。
- 用户：输入用户 ID 或精确用户名，服务端解析为唯一 `site_users.id`；系统/未归属作为单独筛选项，不虚构用户。
- 来源、执行环境、调用状态、费用依据作为次级筛选，默认不展开过多控件。上游供应商只在已有证据时作为明细辅助信息。

用一个分组切换控件提供“供应商 / 接口服务 / 模型 / Skill / 用户”，复用同一张表。服务分组键为 `(billingProvider, service, operation)`，模型分组键为 `(billingProvider, model)`，不把不同计费方的同名模型混成一行；点击分组进入同条件明细。

顶部保留四项：已登记调用、已知估算费用、供应商返回实扣、费用待核对。分组表默认显示调用数、费用及未知数，状态与用量放次级列；单条详情按需展开。后端提供以下指标供核对，不要求全部铺在首屏：

- 外发尝试次数、逻辑请求数、计费项数；
- received/failed/pending/unknown 状态数；
- 输入、输出、缓存 tokens（仅对有该用量的行汇总，缺失单独计数）；
- 已知估算成本、逐笔响应中的已知 actual 成本、未知费用项数；
- 执行环境、币种和费用依据。

金额按 `origin + environment + currency + costBasis` 分桶，不跨桶相加，也不把账单金额加进调用金额。已知实扣可以汇总，完整账单不是前提；显示金额对应的记录数和缺失数。无数据、未知、已确认零费用分别展示。首版复用 `Stat`、`Badge` 和 `DataTable`。

### 4.3 Skill 汇总口径

默认“可加总”视图按模型步骤的实际激活集合归组：

| 步骤事实 | 默认归组 |
| --- | --- |
| 新步骤没有任何激活 | “选择/未激活”，同时保留用户预选或自动选择状态 |
| 恰好一个激活 | 该 Skill + module + version |
| 两个及以上激活 | “多技能/模块共同步骤”，明细列出完整集合 |
| 迁移前步骤，无法证明当时状态 | “历史归属未知”，不归到未激活 |

选择某个 Skill 后，可以查看“涉及该 Skill 的步骤”。如果步骤还涉及其他 Skill，页面标记“含共享步骤，不可与其他 Skill 行相加”。首版不按 Skill 平均或按比例拆钱；这样既满足定位某 Skill 的调用，又保证默认总账不重复。

激活集合说明该步骤实际加载的技能上下文，不证明每个 Skill 对模型费用的独立贡献。同一个 Skill 的两个模块也可能同时激活，展示为共享模块，不冒充两个不同 Skill。工具调用与 Skill 不混为一谈：只有成功的 `load_skill` 形成激活；`read_skill_reference`、`save_draft` 或 `search_xhs_notes` 自己不是新 Skill。

一个 Skill 可以执行多个接口和功能。以小红书为例，实际发生的模型调用和检索调用分别留明细，在该 Skill 筛选下可按接口服务或模型查看；只统计实际外发，不因技能目录列出了某接口就计次数或费用。加载规则、保存稿件等没有供应商外发的本地动作仍留在执行记录，不虚构成本行；共享步骤继续按上述口径去重。

### 4.4 调用明细

每行显示：

- 外发登记时间、计费供应商、service、operation、model；已知上游在详情中补充；
- Skill 激活状态及版本、用户、assistant/session/turn（存在时）；
- run、receipt、attempt 身份；已有运行详情提供链接，其余身份提供复制，首版不新建回执详情页面；
- received/failed/pending/unknown、耗时；
- tokens、供应商 credits、视频秒数等结构化用量；
- 金额、币种、actual/estimated、价格来源、历史/当时快照状态；
- 费用不适用或未知的原因，例如“万相轮询，费用归生成任务”“历史未记录价格”“供应商用量缺失”。

默认按 `(started_at, attemptId)` 倒序，游标分页每页 50 条，最大 200 条。筛选或分组变化重置游标。长 ID 和模型名允许换行，表格自身横向滚动，不造成整页横向溢出；390px 下筛选单列、统计两列，操作按钮保持可见。

DTO 不返回 prompt、附件内容、完整 base URL、请求头、原始响应或原始 error 文本。需要诊断时进入已有受权限保护的运行详情。

### 4.5 已存账单

复用现有 Redfox 已存账单页、精确 decimal 解析和核对边界，只迁移页面归属，不新写一套账单解析。

- 只有管理员在现有平台查询中显式查询账单后，这里才出现新数据。
- 保留“无唯一请求 ID、gmtCreate 时区未声明、分页未证明覆盖完整时段、本地 attempt 不证明送达”的限制。
- 积分面值折算不称为实际现金成本；未知分类不自动当消费或退款。
- 单条账单若有可靠请求标识、币种和账户等匹配证据，可以确认单条对应关系，不需要整期账单完整。只有声称整期账单与本地合计一致、没有漏扣/多扣时，才必须证明范围和分页完整。现有 Redfox 缺少逐笔匹配所需证据，首版仍显示“不可逐笔比较”。
- 此视图继续使用现有 `/api/admin/redfox/costs`，只呈现其已存账单和核对边界。调用概览中的用户、Skill、模型筛选不作用于账单，切换视图时收起这些条件；账单原时区未知时不套用本地调用时段。

## 5. 数据模型与归属规则

### 5.1 不新增第二套调用流水

`receipt_attempts` 仍是唯一调用事实源。新增统计身份与旧执行身份分别承担自己的职责：

| 统计 DTO | 语义 | 来源和规则 |
| --- | --- | --- |
| `billingProvider` | 向本系统计费的服务商 | 适配器及受信配置确认；默认供应商筛选使用此字段 |
| `upstreamProvider` | 计费服务商声明的路由上游 | 可空；从已校验路由或证据取得，不推断为另一笔支出 |
| `service` | 现有服务/预算类别 | 沿用现有 service，例如 `assistant.text`、`redfox.query` |
| `operation` | 实际调用的接口或服务动作 | 稳定 operationId、工具 ID 或适配器动作名，不是 taskId |
| `model` | 调用指定的模型 | 可空；只记已知模型身份，不填接口编号 |

以现有路由说明身份，不依赖在线价目：

| 调用 | 计费方 | 上游 | service | operation | model |
| --- | --- | --- | --- | --- | --- |
| 助手通过已核实的 DeepSeek 直连配置调用 | deepseek | 空 | assistant.text | chat.completions | 模型快照中的实际 ID |
| Redfox 小红书笔记检索 | redfox | 未知则空 | redfox.query | 3X8FGEEM | 空 |
| AgentKey 已声明 TikHub 的查询路由 | agentkey | TikHub | agentkey.query | 对应 route.tool | 空 |
| Redfox 图片生成 | redfox | 未知则空 | redfox.image | 对应提交接口 ID | 已校验的图片模型 ID |
| 百炼万相生成 | aliyun | 空 | aliyun.wan.video | wan.submit | 现有 WAN_MODEL |

**operation 和 model 可以同时有值。** 图片生成、万相提交和文本模型接口都可能同时具备这两类身份；仅无模型含义的查询让 model 为空。代理路由中的模型名称不能证明计费供应商就是模型厂商，自定义/未核实端点保持供应商未知。

现有 `receipts.model`、`receipt_attempts.model` 和 `ReceiptRequest.model` 保持原含义，因为 `logicalKeyFor()`、恢复逻辑、`service_prices` 和其他读取方已经使用它们。新统计的 model 来自新增 `model_id`，不能在原字段上清空 Redfox operationId。统计元数据与价格快照不加入原逻辑键，不影响已存回执复用。

新增调用的归属路径为：

```text
receipt_attempts
  ├─ receipt_id → receipts（逻辑请求与 purpose）
  ├─ operation_run_id → operation_runs（触发本次外发的任务）
  ├─ owner_user_id → site_users（会员归属）
  └─ receipt_id / operation_run_id → 现有助手步骤或工具调用 → turn / session / activation
```

新调用不靠 `operation_results.data` 的有效期维持归属。当前结果过期会保留行及 run/receipt 关系，也可支持历史只读投影；不把现有过期机制描述为删除全部成本关联。

### 5.2 最小 expand-only 迁移

实施时在当前最大迁移编号后新增一个迁移；按当前工作区预计为 `0091_cost_center.sql`，若已有更新则顺延，不改写旧迁移。

#### `receipt_attempts`

新增：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `billing_provider` | `text NULL` | 计费供应商，未知时为 null |
| `upstream_provider` | `text NULL` | 已知路由上游，无证据时为 null |
| `operation_id` | `text NULL` | 统计接口身份；接入本合同的新调用必须提供 |
| `model_id` | `text NULL` | 统计模型身份；与旧 model 字段分开 |
| `environment` | `text NULL` | 执行环境分类，复用现有环境配置 |
| `operation_run_id` | `bigint NULL` | FK → operation_runs(id)，记录触发本次外发的 run |
| `owner_user_id` | `bigint NULL` | FK → site_users(id)，用于会员筛选与汇总 |
| `owner_kind` | `text NULL` | member/admin/system/unassigned；null 表示旧记录未捕获 |
| `price_snapshot` | `jsonb NULL` | 当时选定费率和来源；或结构化的无法估算原因 |

取舍：删除通用 `cost_context` JSON 归属容器。用户与任务是核心查询维度，使用数据库类型、外键及定向索引；session/turn/step 通过已有持久关系读取，不在 attempt 重复存一套。价格快照仍适合 JSON，因为它保存不同计量方式的不可变证据，不承担用户归属查询。

写入合同：

- 新适配器以一个经过校验的 `costIdentity` 参数提供计费方、上游、operation、model；`paidRequest()` 映射到上述字段。`operation_id` 存在时采用新身份，`model_id=NULL` 不回退成旧 model 中的接口编号；未接入的新旧调用仅在可证实的白名单中做历史投影。
- `receiptOptions()` 沿既有 `beforeClaim` 返回已锁定 run 的 ID、ownerKind 和 userId；`member` 必须有 userId，其他 ownerKind 不带会员 ID，数据库 CHECK 校验组合。外键不使用级联删除，删除用户/任务不得连带删除成本事实。
- 系统调用和管理调用从实际入口、已验证 actor 确认 ownerKind；缺乏证据用 `unassigned`，不能把“没有 userId”一律解释成系统调用。无需虚构 run。
- 现有锁定流程校验 run.actor 与 owner_user_id 一致；数据库 FK 只保证引用存在，不冒充跨表业务校验。复用回执时不改归属，真实重试的新 attempt 才冻结新的触发 run。
- `environment` 从现有 `config.environmentName` 归一为 production/development/test/other；历史无法确定则 unknown。不根据官方端点、`origin=live` 或 `NODE_ENV` 单独判断生产；不同环境的官方付费调用保留各自费用。

`price_snapshot` 使用有版本的结构。`state=ready` 时保存十进制费率字符串、币种、计量单位、旧价目查询键、选价时间、来源/核验日期及必要的供应商规则版本；`state=unavailable` 时保存 `missing_price`、`invalid_price`、`unsupported_rule` 等有界原因。旧记录保持 null。该快照不保存秘密或执行任意规则脚本。

#### `assistant_model_steps`

新增 `cost_context_version smallint NULL`（首版值为 1）。它只标记模型步骤的激活集合已捕获，旧步骤为 null，以区分“当时无激活”和“历史未知”。

新增 `assistant_model_step_activations`：

| 字段 | 约束 |
| --- | --- |
| `model_step_id` | 引用 `assistant_model_steps(id)`，联合主键之一 |
| `activation_id` | 引用 `assistant_activations(id)`，联合主键之一 |

创建模型步骤时，在与 `activeTools()` 相同的事务和激活集合上保存全部有效 activation。可让 `activeTools()` 返回 `{tools, activations}`，由步骤创建事务同时保存，避免工具和成本各自查询出不同集合。不能事后把后续激活回填到先前步骤。

这是步骤与现有 activation 的关系表，不复制 Skill 目录，也不新建费用流水。关联必须属于同一 turn，校验和步骤写入在同一事务完成。

#### 索引

增加支撑实际查询的少量索引：

- `receipt_attempts(started_at DESC, id DESC)` 支撑时间范围和游标；
- `receipt_attempts(billing_provider, started_at DESC, id DESC)` 支撑常用供应商筛选；
- `receipt_attempts(owner_user_id, started_at DESC, id DESC) WHERE owner_user_id IS NOT NULL` 支撑核心用户查询；
- `receipt_attempts(operation_run_id) WHERE operation_run_id IS NOT NULL` 支撑任务关联；
- `assistant_model_step_activations(activation_id, model_step_id)` 支撑 Skill 反查；
- `assistant_model_steps(receipt_id)` 支撑历史模型步骤关联（若实施时已存在则不重复创建）。

复用现有 service 时间索引。其余接口/模型索引通过代表性数据的查询计划决定；不预建所有维度组合的索引，也不以“先做时间过滤”替代用户这一核心筛选的索引。

### 5.3 归属优先级

1. **新 attempt**：使用冻结的 operation_run_id、owner_user_id、owner_kind；同一成本项只归属于触发该次外发的一方。
2. **历史助手模型**：可通过 `assistant_model_steps.receipt_id → turn → session` 唯一恢复用户；Skill 状态仍为历史未知，不能从后来的 activation 反推。
3. **历史普通任务**：可用已有 run/receipt 关系恢复，但若同一 attempt 对应多个不同用户/任务且无法证明唯一所有者，标记“归属冲突/未归属”，不能复制成本到每个用户。
4. **历史身份**：只使用适配器语义、已存快照和端点/配置证据可证明的映射，输出 `identitySource=legacy_mapping`。Redfox 的旧 model 投影为 operation；已知 LLM 的旧 model 投影为 model。同名模型不能证明计费方，`assistant.text` 无可靠供应商证据时保持未知。
5. **系统与 Admin**：保留 actor 类型，不归到会员用户。

回执复用没有新外发，不新增 attempt 或成本。后续任务复用别人已存响应时，会员积分如何收仍由既有账本决定，供应商成本不会被复制。

### 5.4 子检索归属

助手子检索通过 `assistant_tool_calls.child_run_id` 关联父回合，再通过该 tool call 的 `activation_id` 归属 Skill。新 attempt 只冻结 child run 和用户，父 turn/session 使用现有关系。

当前 `prepareSearch()`/人工批准会校验 `input.activationId`，但 `startSearch()` 未写入 `assistant_tool_calls.activation_id`。实施时在公共启动路径使用既有 `activation()` 校验，并与 child_run_id 一起持久化该 FK，覆盖人工和自动确认；不能仅在人工路径补写。历史字段为空时只允许将 input.activationId 与同一 turn 的真实激活记录核对后作只读投影，标明历史来源；校验不成立则未知，不批量猜测回填。

因此：

- 子查询的用户来自父 session owner；
- Skill 来自实际触发查询的 activation；
- 查询重试仍是独立 attempt，但沿用同一 child run/Skill；
- 普通非助手工具任务没有 Skill，显示“不适用”，而不是“自动选择”。

## 6. 价格与费用口径

### 6.1 外发前冻结价格

在 `paidRequest()` 创建 attempt 的同一占位事务中，用固定的本次登记时间读取/选择费率并写入 `price_snapshot`。保持既有业务锁 → 预算/回执锁顺序，不在锁内请求外网。

- 普通固定费率复用 `service_prices`。`ReceiptRequest` 可提供独立的 `pricingKey={service, model}`；这里的 model 是现有价目键，可以是接口编号，不与统计 DTO 的 model 混用。助手显式使用已冻结模型配置中的价格服务/模型键，而不是 `assistant.text`。
- 仅有供应商特殊规则时，适配器提供可选的 `resolvePriceSnapshot(tx, context)` 本地函数；通用入口只负责调用和持久化，不内置各供应商的分时规则。其输入为同一次外发登记时间、已有价格配置与非敏感参数，输出选定费率或无法估算原因。
- 对 DeepSeek 等确有分时规则的服务，首版只实现实际需要且已核验的供应商局部选择函数，写入来源、时区、规则版本和选定费率。基础价格仍由已有价目维护；局部函数不再保留第二份可编辑价格表。尚无可靠规则/价格或处于无法判定的时段边界时，保留未知或明确的标准价估算，不能冒充精确实扣。
- **不向 `service_prices` 增加通用 `schedule` 字段，也不建设规则编辑器。** 将来有实际且稳定的共同需求再提取共享逻辑，不以供应商数量作为机械门槛。
- 万相继续使用现有任务价格快照，不重新通过模型 token 价目计算。

占位事务把刚持久化的快照作为回调参数传给适配器，例如 `paidRequest(req, async context => ..., options)`；旧的无参回调兼容。适配器只能使用该 context 的快照计算本次估算，不再查询当前价。恢复复用不调用适配器、不改写快照；真实重试新增 attempt 并捕获重试当时费率。计价元数据不改变原请求身份。

本次新增的成本估算配置缺失或无效，记录 `state=unavailable` 及原因，按原预算、权限和已批准价格规则决定是否外发；不新增“统计价格错误就停用户任务”的门槛。既有会员准入、成本安全检查、凭据校验照常执行。数据库或回执持久化失败仍按原机制停止，不能因为统计降级而绕过回执。

本文不新增或确认任何供应商现价。实施接入实际价格时核对官方来源，测试用明确标注的合成费率。

### 6.2 谁在何时计算估算

`paidRequest()` 负责冻结证据，不根据 HTTP 状态猜测供应商是否计费。适配器根据可验证的用量/计费证据，使用冻结快照与纯计价函数返回 `CallOutcome.cost`：

- 响应明确提供本次费用与币种：保存 `basis='actual'` 及对应请求证据；
- 无逐笔 actual、但有适用单价和有效计量证据：保存 `basis='estimated'`；按次接口的计量按原适配器合同判定，不能要求所有接口都有 token usage；
- 既无可靠逐笔 actual，也不满足估算条件时：`cost=NULL`。可信 actual 不因缺少本地单价或 tokens 被丢弃；
- failed/unknown 不自动等于免费，也不自动等于收费；只有响应证据支持时才登记费用；
- 文档明确的免费请求可记录 0，不能把缺失价格当 0。

保留原始响应先落库、业务解析后提交的流程。可选计价解析遇到缺字段、单位冲突、溢出等情况返回未知及有界诊断，不抛错丢掉已收到响应，不将成功响应变为需要重复外发的失败。业务解析和供应商错误分类仍按原机制处理。

沿用现有 cost/currency/cost_basis 字段。为避免新路径通过浮点中转，将 `CallOutcome.cost.amount` 增量兼容为十进制字符串或既有 number；新估算使用字符串写入 numeric，旧调用方可继续工作。成本中心对历史已存金额按原值和依据展示，不能用新规则覆盖旧金额。首版账单查看不会回写 attempt 的 cost。

### 6.3 DeepSeek 与通用模型 usage

助手 `responseUsage()` 在现有三个字段外，白名单保留 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`；普通模型适配器同样保留可信字段。不得从未知嵌套结构猜缓存量。

缓存价计算必须满足：

```text
输入费用 = (缓存命中 tokens × cached_per_mtok
          + 缓存未命中 tokens × input_per_mtok) / 1,000,000
输出费用 = completion tokens × output_per_mtok / 1,000,000
估算合计 = 输入费用 + 输出费用
```

验证 token 数非负、缓存子集不大于总输入，不能把 prompt 总量和缓存命中量重复相加。如果只给 prompt 总量而没有命中/未命中拆分，则不能声称使用了缓存价；按已明确的标准输入价估算时必须标明“不含缓存优惠”，否则显示未知。不能用缺失字段自动补 0。

金额使用十进制/定点计算，沿用 SQL `numeric(14,6)`；每条成本入库时统一舍入到 6 位，总额按已存每条金额求和，DTO 返回字符串。测试示例：合成未缓存输入价 2 元/百万、1,000 tokens、输出 0，应为 0.002000 元，不能算成 2,000 元；这不是供应商现价。

### 6.4 普通 attempt 与特殊计费项

成本中心同时有“调用”和“费用项”两个概念。费用项只是在查询时按 attempt 或既有万相任务去重得到的行，不新增费用事件表、事件总线或第二套持久流水：

- 普通服务：一个 attempt 是最多一个费用项，重试各有自己的证据；同一 receipt 的恢复复用不产生新项。
- 万相：以 provider + 配置身份 + taskId 去重，费用锚定原始提交 attempt；终态轮询提供秒数证据，但轮询行标为“费用归生成任务”，不是未知费用，也不再加一次钱。
- 万相尚未终态：提交调用保留，费用可未知；终态证据冲突时进入待核对，不能选一个有利数字。
- 其他未来特殊服务：只有当实际计费单元不是 attempt 时，才增加类似的局部证据读模型。

复用并适度扩展 `wanTaskCosts()` 的规范化结果，让统一读模型取得提交 attempt、run 和去重任务身份；在原函数内统一十进制处理，供新旧入口共用，不复制其乘法和去重规则。通用汇总排除已由特殊费用项接管的金额；轮询行保留调用次数但费用不适用，提交行呈现唯一任务费用。费用的所有维度和时间归属沿提交 attempt；日期过滤不得截断其他日期到达的终态证据。同一任务存在冲突证据则显示待核对。

### 6.5 actual、estimated 和会员积分

| 口径 | 含义 | 能否混合 |
| --- | --- | --- |
| 调用 actual（DTO `perCallActual`） | 供应商响应明确给出的本次费用 | 按当前筛选汇总已知记录，无需整期账单完整；展示覆盖数 |
| 账单实际扣费（DTO `billActual`） | 已存供应商账单中已确认的消费金额或单位 | 仅在账单视图展示；与调用费用不相加，完整性决定能否做整期对账 |
| estimated | 按当时官方单价与已存用量估算 | 可单独汇总，必须标“估算” |
| 供应商 credits | 供应商账户单位 | 不自动换算成 CNY，除非有明确且适用的兑换证据 |
| 会员积分 | 系统向用户预约/消耗的积分 | 与供应商成本完全分开 |
| 未知 | 没有足够证据 | 不是 0 |

`perCallActual` 与 `billActual` 是页面读取的不同证据集合名称，不新增两套成本流水或扩展现有 `cost_basis` 枚举；账单视图可从原有响应投影，不改既有账单 API 结构。账单只有供应商积分时仍返回该原始单位；面值折算继续单列，不能包装成 CNY 实扣。同一笔支出出现在响应和账单中也不能相加。

例如选定时段有 3 次调用，其中 2 次明确实扣合计 1 元，另 1 次只有估算 0.2 元：展示“已知实扣 1 元 / 2 次、估算 0.2 元 / 1 次”，不能因缺完整账单隐藏 1 元，也不能将 1.2 元称为全部真实支出。统计时间始终按调用登记时间；账单使用自身原时间，未匹配时不强行拉齐。

首版成本中心不计算会员收入或毛利。任务链接可进入现有积分详情；未来若增加对照栏，必须按 root run 关联 `member_credit_charges`，单独显示 reserved/consumed/released，不能加进供应商成本。

## 7. 后端读模型与 API

### 7.1 单一读模型

新增 `packages/backend/src/admin/costs.ts`，负责：

1. 校验时间、筛选、分组和游标；
2. 构造同一套过滤后的 attempt/费用项集合；
3. 关联用户、助手、Skill 和供应商证据；
4. 计算汇总、分组和明细；
5. 返回不含敏感内容的 DTO。

HTTP 层只做 admin 鉴权和 DTO 传递，前端不拼 SQL、不重算成本、不自行推断供应商。

概览总数、分组和明细共享过滤条件及费用项定义。先保证 attempt/任务费用项各自唯一，再关联 Skill；用 EXISTS 或预聚合避免一个 attempt 因多个结果/激活记录被展开成多行。特殊万相费用与普通 attempt 使用明确的 union/排除关系。Skill 的“涉及”筛选对每个调用只返回一次，跨 Skill 视图不能再求和，响应带 `additive=false` 和解释。

一次响应内需要多条 SQL 时，用只读一致性事务取得该视图所需数据；输出读取时间。正在执行的调用后续可能补充费用，刷新/下一次请求可以变化，首版不建设长期报表快照。SQL 在时间范围内做过滤/分组并限制返回数量，不在 Web 下载全量回执再汇总。概览与明细共用口径，不意味着每次请求同时计算两者；分页只约束返回量，不能代替汇总性能验证。具体保护见第 7.3 节。

### 7.2 API

新增只读：

```text
GET /api/admin/costs
```

主要查询参数：

| 参数 | 规则 |
| --- | --- |
| `start`, `end` | 含时区 ISO，start < end，最多 92 天 |
| `view` | 仅 `overview`、`details`；账单不进入此 API |
| `groupBy` | 概览当前分组：`provider`、`service`、`model`、`skill`、`user`；明细不执行分组 |
| `billingProvider`, `service`, `operation`, `model` | 有界字符串，精确匹配统计身份；provider 分组默认指计费方 |
| `skillId`, `moduleId` | 有界 ID；查询“涉及该 Skill”的调用 |
| `userId` / `username` | 两者互斥，分别按整数 ID 或精确用户名解析；纯数字用户名也不冒充 ID |
| `owner` | `member`、`admin`、`system`、`unassigned`，可选 |
| `origin`, `environment`, `status`, `costBasis` | 白名单枚举 |
| `cursor`, `limit` | 稳定游标，默认 50、最大 200 |

响应按 view 区分，未请求的结果不计算，也不填 0 冒充已计算：

- `query`：规范化条件、时间基准和读取时间；
- `overview` 的 `totals`、`groups`：整个筛选范围的总计与当前一个分组维度，包含调用、状态、usage、费用桶和未知计数；不附带明细列表；
- `details` 的 `details`、`nextCursor`：按 `(started_at,id)` 游标取当前页，不计算全范围总额、分组或总页数；概览分组也有限额并返回后续游标，不能只取前 N 项而伪装完整汇总；
- `facets`：已有供应商、服务、模型和 Skill 选项，数量有上限，未知项保留；优先复用目录，不为明细翻页反复扫描整表生成候选项；
- `warnings`：历史未知、归属冲突、异常万相证据、不可加总共享步骤等；概览对应整个筛选范围，明细仅说明当前页，不额外扫描全范围计算警告数；
- `selectedUser`：用户筛选解析后的显示名和用户名。

未查询到的用户返回“该用户不存在”，不自动取消条件变成全部用户。概览总额覆盖整个筛选范围，与当前分组/明细页不同；分页和币种/环境桶均标明范围。明细页提供“查看同条件汇总”链接，不暗中再请求概览；返回概览时允许重新读取并标注时间。候选项截断时说明限制，并允许用已知精确 ID 筛选。

账单接口固定继续使用 `GET /api/admin/redfox/costs?start=...&end=...&billRunId=...`，参数和响应结构保持兼容，不在首版新设 `/costs/billing`。成本中心的账单视图仅消费 `billPages/selectedBill/comparison`；旧返回中的 `local/wan` 若仍保留，改由统一成本读模型和既有万相函数生成兼容结构，移除重复本地聚合 SQL。统一成本读模型不反向调用这个兼容入口，避免循环依赖。账单校验及精确金额解析继续复用原函数。

所有路由沿用 `adminHandler`，GET 不改数据，后台响应禁止共享缓存。会员不能访问，匿名不能访问，普通前台 API 不暴露成本数据。

### 7.3 查询保护与按需计算

以下为首版局部约束，实施时在现有读模型、连接池和 HTTP 错误处理内完成，不引入独立报表服务。

#### 查询保护

- 复用 `db.ts` 的连接池；参照现有搜索入口的容量保护方式，在成本模块内加一个简单的并发上限，不复用搜索专用队列和缓存。默认每个 API 进程最多 2 个成本请求执行，已有连接池容量小于 4 时降为 1；超额直接返回 503 和短 `Retry-After`，不建立等待队列、不扩大连接池。新成本接口与旧账单兼容入口共用此上限，一次请求只占一次名额、最多一条连接；下层万相等读取函数传入并复用同一事务，不能内部再取全局连接或重复获取名额。
- 成本读取使用短只读事务；多条查询需同一快照时采用 repeatable read。事务内局部设置单条 SQL 超时 5 秒、锁等待超时 500 毫秒，整次读取含连接等待预算 8 秒；这些是待验收的初始值，不改变全库参数或现有写入超时。复用 `adminGet()` 的取消传递和当前 30 秒 HTTP 上限，数据库保护必须先于 HTTP 上限生效。
- 取消或达到总时限时终止待执行/执行中的数据库查询，回滚后释放连接和容量名额；不能只让前端停止等待、后台继续算，也不能在 SQL 尚未结束时提前释放名额。查询忙或超时显示“统计暂时繁忙，可缩小时间范围或稍后重试”，保留筛选条件，不自动连续重试、不返回部分总额或用 0 代替失败。
- 统计不获取任务、预算或积分的业务行锁，不调用收费执行逻辑。进程内限额只限制本进程，不保证跨进程全局容量或业务连接预留；若实际部署多个 API 进程，按进程数验证总并发，先下调局部上限，不在首版新增分布式限流。

#### 按需计算

- `overview` 只算总计与当前选中的一个分组；`details` 只取一页。SQL 先完成时间、用户、Skill、费用依据等真实筛选，再分页；名称和展示信息仅批量补齐当前页，不能先分页再过滤而漏行，也不逐行查询用户/Skill。
- Skill 通过既有关系做 EXISTS 或预聚合；小红书等一个 Skill 的多个接口可合并查看，同一 attempt 只出现一次。历史归属推导也先限定候选回执，不为一个用户查询遍历全部历史。
- `wanTaskCosts()` 当前会读取全部历史终态证据并逐任务查询提交记录。复用其计价、冲突和去重语义，同时将读取改为按候选提交/任务身份批量关联证据；日期只约束提交，不能裁掉跨日终态证据。查询次数不得随任务数逐项增加；需要的定向索引由查询计划证明，不另建费用表。
- 筛选输入经现有 GET 表单提交后查询；分组切换、翻页和主动刷新各读取一次。页面不同时加载所有视图、不自动轮询；快速切换取消旧请求，旧响应不能覆盖新条件。候选和分页复用现有目录/路由机制，不新增多层缓存状态。

首版继续采用 SQL 直接聚合，不加 Redis、预汇总表、物化视图、分区、异步报表任务或额外数据库。若第 11.5 节实测不达标，先定位扫描、关联、排序或连接等待，优化相应 SQL/索引和查询范围；仍有瓶颈再单独评估预汇总与迟到费用更新规则，不能用提高超时或静默截断数据代替修复。

## 9. 新模型、新供应商与百炼接入合同

普通新接入只需满足现有付费调用边界和以下四项：

1. 继续经过 `paidRequest()`，不直接绕开回执和预算；
2. 保留既有执行身份，在新增 `costIdentity` 声明稳定的计费方、可选上游、operation、可选 model，沿用 service；无模型含义的 API 不用 operationId 冒充统计模型；
3. 提供可信 usage，以及响应 actual cost 或可用于估算的价格键；特殊选价仅使用供应商局部函数与不可变快照；
4. 用户任务继续通过 `receiptOptions(execution)` 记录强类型 run/owner；助手 Skill 由现有激活关系提供，不由供应商或用户输入决定。

完成这些后，已支持的计量方式自动获得明细、分组和筛选，无需修改核心页面。未知计价方式先显示用量及未知金额，不能承诺任意新服务零适配即有准确金额；名称优先取现有适配器/模型/工具目录，缺少名称时显示稳定 ID。

阿里云百炼分两类：

- **百炼文本/视觉模型**：直连配置使用现有 `dashscope` 服务身份、模型目录和 token 价格快照，计费方记录为 `aliyun`；经其他供应商路由时按实际计费方登记。
- **万相视频等任务型服务**：沿用任务 ID、提交/轮询关系、输出用量和任务价格快照，以任务为费用项。

只有出现新的计费单元（例如存储流量、按图片张数、按任务且多次终态回调）时，才在对应供应商模块补充结构化 usage 或局部去重读模型。不要为假想的供应商提前实现插件注册、动态脚本或通用表达式引擎。

未来若接供应商账单 API，另增“账单证据 + 对账”能力：保留供应商账单 ID、请求 ID、币种、账单时间和完整拉取范围。能否逐笔核对取决于真实标识，不能用余额差强行分摊到本系统调用。

## 11. 测试与验收

### 11.1 计价与归属

- 纯接口、纯模型、接口与模型同时有值、AgentKey/TikHub 路由均按五类身份正确显示；同名模型由不同供应商计费时不混组；新查询的 model_id 为空时不回退到旧接口编号。
- 普通输入、缓存命中/未命中、输出 tokens 和供应商局部分时规则使用正确快照；覆盖时区边界、无规则和字段冲突，金额未知不得冒充 0。
- 调价前后的两个 attempt 保留不同金额；修改当前 `service_prices` 不改变历史快照。
- 用合成费率验证每百万 token 的除数、缓存子集与输出计量；逐条舍入、精度和总额求和口径一致，小额不因界面截断而标免费。
- 没有完整账单时仍可汇总两条已知实扣；同一响应费用与账单再次出现时不相加。CNY、USD、AgentKey credits、Redfox 积分和会员积分分别处理。
- 首个模型步骤没有激活；加载 Skill 后的步骤才有对应集合；后续再加载模块不回写之前步骤。
- 两个激活共同作用时，默认汇总只计一次；按单 Skill 查看时明确共享、不可加总。
- 人工与自动确认都在公共检索启动路径写入 activation_id；跨 turn 的 activation 被拒绝；历史只读投影有明确证据；非助手工具显示 Skill 不适用。
- 用户/任务 FK、owner_kind 与 userId 组合、run.actor 与用户一致性成立；系统/Admin/历史共享回执不会错误归给会员。

### 11.2 回执、恢复与特殊费用

- 同一 receipt 的多次真实重试分别保留 attempt；恢复复用不新增调用或成本。
- 补成本元数据前后，同一个原请求的 `logicalKeyFor()` 结果相同；Redfox 旧 model/operation 和价目键保持兼容，调价或更改归属说明不会创建新逻辑请求。
- pending/unknown/failed/received 各自展示，状态不被当作是否实际扣费的证明。
- `operation_results` 过期后，新调用的用户/run/Skill 和成本仍可查。
- 万相同一配置下同一 taskId 多次终态轮询只计一次；跨日期到达证据仍归提交时段，窗口外的同任务重复提交也参与冲突判断，逐日分段与整段查询口径一致；轮询行不产生生成费用，未知/冲突任务计数正确。
- 汇总与明细在同一筛选下的可加总费用桶一致；游标在相同时间戳下仍稳定、不重复、不漏行。
- 原预算检查和会员积分预约/消耗/释放结果不变；新增统计价格缺失/无效、计价解析失败不会丢失响应或触发重发。数据库写入失败、原有成本准入与权限拒绝依然有效。

### 11.3 API、权限和隐私

- 匿名和会员访问返回 401/403；Admin 只读成功；非法时间、过宽范围、未知枚举和游标返回明确 400。
- 响应不包含 prompt、附件正文、密钥、完整端点、原始响应、原始 error 或技能资源正文。
- 所有查询仅访问数据库和本地技能目录；以禁止网络的测试证明打开成本中心不会调用供应商。
- 空数据、历史 null、未知供应商、未知用户、冲突归属和多个币种均有可见解释。
- `/api/admin/costs` 不接受 billing 视图；既有 `/api/admin/redfox/costs` 参数、返回结构及账单校验兼容，旧 local 聚合转接唯一读模型后不形成循环依赖。
- 精确用户筛选不存在时不退化成全量；数字用户名与用户 ID 区分；分组和候选项截断可见；同一事务内汇总与明细一致。

### 11.5 性能专项验收

这是实施时的一次专项验收，不要求每次 CI 重跑大数据压测，不新增性能平台。以下数值是待验证目标，不代表现有性能或生产容量；主基准使用单 API 进程、现有默认 10 连接，另验证小连接池时容量上限降为 1。记录实际 CPU、内存、PostgreSQL 版本、连接池大小和 API 进程数，不能把不同环境的结果混为同一基准。

- **数据规模**：先用 10 万条 attempt 校准查询，再以 100 万条为主基准；主基准覆盖至少 180 天，其中近 92 天不少于 50 万条，并包含至少 1 万用户及用户调用量倾斜。关联表按实际关系生成，覆盖历史空归属、小红书单 Skill 多接口、多模块共享步骤、重试、万相多次轮询及跨日终态证据；全部使用合成数据与本地桩。
- **场景与并发**：测 7 天/92 天概览、精确用户与 Skill 筛选、接口分组、明细首/后续页；分别测 1 和 2 个并发成本请求。预热后关键场景各采样至少 50 次，记录 p50/p95、最大值、错误及 SQL 次数，首次读取单列。另用 8 个同时请求验证超额快速拒绝、取消后没有遗留查询或泄漏名额。

| 成功读取的 API 响应 | 初始验收目标（主基准、1/2 并发） |
| --- | --- |
| 明细页，含用户/Skill 筛选和后续游标 | p95 ≤ 1 秒 |
| 最近 7 天总计与一个分组 | p95 ≤ 1 秒 |
| 92 天总计与一个分组 | p95 ≤ 3 秒 |

- **正确性与查询计划**：在上述正常并发下不能靠超时/拒绝降低延迟样本；两者单列计数，预期为 0。用 `EXPLAIN (ANALYZE, BUFFERS)` 检查关键查询，核对时间/用户索引、连接行数、排序和磁盘临时读写；宽范围允许合理顺序扫描，不机械要求所有查询命中索引。50/200 条分页及更多万相任务不能引起逐行 SQL 增长；全范围合计与基准数据一致，不抽样或截断求和。
- **业务影响**：在同一独立测试库，以固定的 5 并发运行既有回执落库、预算检查和积分预约/消耗/释放路径，分别测无成本查询、叠加 2 个成本查询时的写入延迟。写入 p95 增量不超过基线的 20% 或 50 毫秒两者较大值，且无新增超时、死锁、重复扣分或恢复差异；没有真实外发，不消耗供应商测试预算。
- **失败处理**：注入慢 SQL、锁等待、连接等待和请求取消，确认在第 7.3 节限时内终止、连接归还，页面可手动重试；明细翻页没有全范围聚合，改变分组没有同时计算其他四个维度。未达目标如实记录瓶颈和修正结果，不只提高超时或改大连接池；需要改变目标时说明环境与数据依据。

### 12.3 复用与最小实现

- **没有第二套调用账本**：复用 `receipt_attempts`，只补证据，不复制每次请求到新流水表。
- **没有第三套费用统计**：统一读模型接管 Redfox 本地分组；旧数据工具费用页重定向；模型页不再按当前价独立估算。
- **没有供应商平台**：只在现有回执入口增加身份、快照和归属合同。新普通供应商不改前端，特殊计费才局部扩展。
- **没有不必要的新表**：只新增多 Skill 步骤关系表；供应商、用户、Skill 不建镜像维表，沿用原始 ID 和现有权威。
- **没有不必要的新组件**：页面全部由现有后台组件组合，URL GET 复用路由和 admin API，不做新 UI 框架。
- **定价范围收缩**：复用现有价目，供应商局部函数处理实际特殊规则；首版没有通用 schedule、规则编辑器或新账单 API。
- **性能措施限定在现有模块**：只补有界查询、批量读取、取消/限时、小型并发保护和专项验收；不预建缓存、预汇总、报表队列或监控平台。
- **必要复杂度保留**：统计身份与幂等字段分离、核心归属字段、价格快照、多 Skill 集合、万相去重、权限和历史未知均对应已发现的真实问题。

### 12.4 架构与扩展性

该边界符合现有模块化单体：供应商适配器负责事实和计价证据，`paidRequest()` 负责外发前的持久化，成本读模型负责查询，API 负责鉴权与组合，Web 负责展示。

百炼文本模型可复用 token 价格，万相任务计费复用既有证据。新服务按已支持的计量合同接入可以复用核心页面；新计费方式仍需适配与验证，不预先承诺准确金额。

### 12.5 首版限制与尚待实施的验证

1. 历史缺失的供应商、用户、Skill 和价格可能永久未知；能安全恢复的部分标为历史映射，不能冒充当时快照。
2. estimated 不是供应商实收，actual 也必须有可信供应商证据；余额差不能逐笔归因。
3. 供应商 credits、会员积分和 CNY 是不同单位，首版不做汇率或毛利。
4. 多 Skill 共享步骤没有客观唯一拆分办法，因此保留共享事实，不输出虚假的“单 Skill 总成本”。
5. 成本中心不是金额熔断器，现有预算仍只限制调用次数。
6. 已存 Redfox 账单在当前证据限制下仍不能证明完整逐笔对账。

复审确认目标与首版边界可保留，五项意见已按实际适用范围修订。剩余工作属于实施验证：增量迁移与旧回执兼容、真实供应商价格来源核验、查询性能和大小屏体验。目前没有实施或验收通过的结论，也不扩大到自动对账、金额预算、会员定价和部署。
