## 1. 目标、承诺与明确取舍

目标：让复用同一组业务能力的多个技能，通过**技能原包和少量兼容配置**接入现有助手，减少逐技能修改静态目录、动作、权限集合和工具绑定的代码接线、评审及发版。

收益基线是**当前已经复用组件、队列、报价、供应商 operation 和账本的系统**，不能按每接一个技能都从零建设这些功能估算节省。公众号精确接口、助手媒体输入/交付等是新功能投入；目录动态化、导入和绑定管理才是额外通用化投入，两者分别记录，见§9.4。

首版采用“**原包不可变保存 + 固定注册数据 + 旁挂运行绑定 + 现有受控工具执行**”。模型按原规则组织任务，宿主负责工具、权限、付费、交付与恢复。本轮实现研究写作与单次图片生成，并用`image-generator`、外部`claude-image-generation`子集和M2独立外部`ai-image-generator`的Direct核心流程验证同一能力复用；单次视频生成仍是后续能力，未在本轮实施。

必须区分三个结论：

1. **原包保持不变**：保留上游 `SKILL.md`、参考资料、脚本和来源身份，不伪称重新编写的规则是原版。
2. **流程可以执行**：原包所需操作已绑定到系统实现的能力，研究、生成、保存均有真实执行记录。
3. **原始脚本原样执行**：首版不提供这个承诺。Python/Node 文件可以归档和检查，**不直接执行联网脚本**；绑定说明明确其功能由哪个受控工具承担。

这比“导入任何合规包即运行”更窄，也比现有逐技能手工改业务代码更通用。Agent Skills 规范定义包格式，并不统一 API、工具、价格、任务恢复或输出展示。若验收目标改成“任意原 Python 必须实际执行且无需适配”，本方案不满足，须另评估隔离执行器；不能用保存了脚本冒充已运行。

首版不建设任意代码沙箱、透明 HTTPS 拦截、CLI 模拟器、动态函数加载、通用工作流 DSL、插件市场、自动安装依赖或多租户容器调度。本轮只使用受控能力，不因后续增加同类技能重复建设这些基础设施。

## 2. 兼容范围

| 内容 | 首版处理 | 边界 |
| --- | --- | --- |
| 标准 `SKILL.md`、名称/描述、Markdown 规则 | 人工审阅后保存、校验、按需加载 | 本轮没有运行时导入/上传；格式正确不代表可执行 |
| `references/` 与文本模板 | 按声明的资源范围读取 | 只在包内解析；大小、路径、hash 校验复用现有原则 |
| `scripts/`、`assets/` 等原包文件 | 完整保留并标明用途 | 脚本不执行；二进制模板不自动获得处理能力 |
| Codex/WorkBuddy 附加显示字段 | 映射可识别名称/描述，保留来源元数据 | 专属工具、连接器声明、`allowed-tools` 不自动授予权限；关键依赖不能静默忽略 |
| 研究写作 | 工具检索 → 有来源的分析 → 保存正文 | 首个实例为公众号；必须有真实研究，不能降级材料写作 |
| 图片生成 | 已绑定现有Redfox图片operation | 本轮只开放`gptImage2`、`1k`、单张、无参考图；不支持编辑、mask或批量 |
| 图片参考图编辑 | 后续能力 | 本轮输入仍为文本附件加图片提示词，不能宣称支持上传参考图 |
| 视频生成 | 规划，本轮未实施 | 不把现有视频工具代码存在当成助手视频能力已接通 |
| 同一服务新增技能 | 增加原包、binding和`skills/registry.json`记录 | 业务执行代码无需按skillId分支；端点、输入、脚本核心处理、编排或交付类型变化仍须另做能力 |
| 任意 MCP、HTTP 地址、SDK、Shell/Python、GPU 渲染 | 不支持直接导入执行 | 未来确有新业务依赖时按能力接入一次；本轮不做通用连接器平台 |
| 自动发布、充值、支付、供应商遥测上报 | 不开放 | Redfox 余额不足仍只在后台对应服务区域提示 |
| 多模型竞赛、批量生成、整条视频剪辑/配音/字幕流水线 | 不在验证范围 | 不通过一份大 skill 隐式扩展动作、价格和模型调用上限 |

规划中的导入预检应向管理员显示：**可启用 / 缺少配置 / 需要新增能力 / 包不合规**及具体原因。本轮未建设该上传/导入界面，只实现固定目录注册；现有后台技能页负责启停与健康检查。能力检查不等于自动证明脚本安全或流程正确，原包核心能力缺失时不能降级运行。

### 2.1 脚本核心逻辑的兼容检查

人工阅读实际入口、其调用的包内辅助脚本及关键依赖说明，沿“输入→处理→请求→结果”确认必要行为；不执行原脚本，不仅搜索 API 地址或检查 Python 是否可安装。只检查会影响当前技能目标和结果的逻辑，不逐文件建立评分体系，也不建设自动代码语义分析器。

| 检查项 | 需要确认的事实 | 兼容判定 |
| --- | --- | --- |
| 输入预处理 | 裁图、拼图、压缩、编码转换、文本清洗等是否是必要步骤 | 有现成能力可接管；缺少必要处理则标记需要新增能力，不能直接跳过 |
| 计算与参数转换 | 尺寸/比例/时长计算、字段映射、排序、去重、批次拆分是否影响结果或价格 | 固定值和已支持选项可以配置；新算法不能塞进绑定表达式或让模型猜算来冒充确定性处理 |
| 调用编排 | 一次流程实际请求几次，是否有依赖的多阶段生成、扩期、上传或循环 | 必须由当前能力及次数/批准规则完整覆盖；不能把多次生成包装成一次工具费用 |
| 状态与错误分支 | 重试、taskId 保存、断点续查、空结果、部分失败如何处理 | 对应现有持久任务与回执；有意收紧重试/扩期等策略须记录差异，不用整脚本重跑替代恢复 |
| 结果后处理 | 下载之后是否还要转码、剪辑、字幕、排版、格式转换才能算完成 | 保存原始文件不等于完成这些步骤；缺少核心处理不宣称已支持整个技能 |
| 其他依赖和外部动作 | 专属 CLI/MCP、本地模型、视觉分析、运行环境、支付/发布/遥测 | 缺能力明确列出；禁止的动作不获执行权限，不能从标准格式推导授权 |

每个包在既有验收记录中保留一个简短映射表：`原行为及文件/函数 → 必需或可选 → 对应已有能力/配置 → 差异与核心样例证据 → 已覆盖/需新增/不支持`。证据须验证对应处理后的交付结果，不仅确认存在类似工具。可选功能若不开放，要同步缩小入口描述；核心行为缺失或判断不清时不能标为可启用。需求理解、选样、分析、写作及自检由模型遵循Skill规程，不再逐步骤硬编码；必要的确定性数据处理、权限、付费动作的依赖与批准顺序、回执保存和重试/恢复由宿主负责。研究交付核验真实工具结果、分析和引用归属，不等于控制模型内部思考顺序或保证内容质量。

兼容配置只表达已支持能力的选择、资源和固定选项，不允许嵌入代码、条件循环或任意转换表达式。若映射必须新增业务逻辑，这次应记录为“能力开发”，不归入“仅配置接入”，也不为维持零代码结论隐藏在巨大绑定文件里。

## 4. 最小结构：配置描述技能，代码实现能力

```text
原始技能包 + 运行绑定
           ↓ 校验、注册、启停
现有助手：选择 → 读规则 → 提问/提出工具请求
           ↓ 固定能力合同、规范化参数
现有费用确认 → operation/队列 → 供应商回执/预算
           ↓ 安全结果、真实资产
现有会话进度 + 稿件/媒体面板 + 成本中心
```

### 4.1 导入与版本管理（本轮仅固定注册）

- 总体规划提供管理员维护用的**本地包校验/注册命令**；本轮未实现该命令或安装器，只由发布版本携带并校验固定`registry.json`。不新增ZIP上传页面、任意Git URL拉取、市场搜索或自动更新。
- 安装范围限管理员预先审阅的包；会员没有上传可执行技能的入口。校验只读取文件，不执行脚本、安装依赖或试调用供应商。
- 原包保存在 API/Worker 共用的私有技能资源目录，按内容 hash 不可变存储，业务接口不直接公开该目录。先完成校验和文件原子发布，再注册索引；发布失败不产生有效候选。
- 注册信息、当前版本指针及能力绑定由发布携带的固定registry/binding维护；包manifest记录版本/hash，运行时校验后缓存。settings与审计只管理允许运营新任务和revision，唯一权威仍是skill-policy。新包默认关闭。
- API/Worker使用同一发布的固定注册目录并校验完整性；提交准入锁定并核对运营策略revision，任务冻结候选包/hash。本轮没有运行时注册修订服务，目录校验使用进程缓存。缺文件/hash不符时拒绝新请求，不能仅信前端列表。
- 历史任务冻结包、绑定、能力合同版本；旧版本不可原地覆盖或由当前版本替代。旧包至少保留到相关任务结束及历史追溯不再依赖它；本轮不做自动垃圾回收。
- 原生 `general-writing/xiaohongshu-creator` 的标识和已发布版本不能被导入包覆盖。外部重名必须明确命名，不能自动顶替。

### 4.2 旁挂绑定的内容

绑定只声明显示名称、动作、原包资源范围、已实现能力标识、输入与交付合同、必要运行差异；不允许注入任意函数、供应商 URL、请求头、密钥、用户身份、价格或免确认规则。

示意（**拟议配置，不是已存在 API/schema**）：

```json
{
  "formatVersion": 2,
  "skillId": "wechat-write",
  "sourcePackageHash": "<固定原包hash>",
  "entry": "SKILL.md",
  "action": { "id": "wechat-write", "label": "公众号创作", "profile": "creative" },
  "inputContract": "writing-input@1",
  "capabilities": ["wechat-hot-articles@1", "wechat-research-analysis@1", "save-text@1"],
  "deliveryContract": "wechat-research-writing@1",
  "references": ["references/gzh_trend_data_format.md"],
  "scriptBindings": [
    { "path": "scripts/fetch_gzh_trends.py", "handledBy": "wechat-hot-articles@1", "executeOriginal": false }
  ]
}
```

`scriptBindings` 是给模型及管理员看的对应关系，不是 Shell 命令拦截器、参数转换语言或脚本执行授权。宿主加载原规则时同时提供这一说明；模型使用已公开的类型化工具。不能通过识别一段 Python 文本自动猜出正确接口。

原始写作规则尽量直接复用，系统运行差异集中在绑定说明，不要求每包重写整篇 SKILL.md。参考文档只读允许集合；支付、自动安装、外部上报段落不获得运行能力。来源、使用依据和固定提交沿现有外部包规则记录；未确认许可的包不因导入成功自动变成可公开分发的商业素材。

### 4.3 能力分发与入口

- 在 assistant 功能内维护有限的代码定义能力表：输入 schema、准入/报价、事务创建、结果投影、交付校验和可观察事件。它是现有工具分发的整理，不建设动态 provider registry 或可执行插件系统。
- 目录包列表、动作及依赖说明改为由已验证绑定生成；同时生成 `creative` 的有效 skill/module/tool 集合，候选选择与工具权限交集必须使用这同一集合，并随任务冻结。仅增加菜单不能通过接入验收。原生 profile 的固定范围及旧任务快照保持；新绑定不能扩大小红书专属入口权限。
- 新增技能进入现有 `creative` 综合入口，技能下拉、欢迎快捷动作和模型候选共用后端目录。
- 首版不为公众号、图片、视频分别增加助手路由/窗口，不把 `AssistantId` 全面动态化；现有小红书专属入口保持。公众号专属入口从旧方案顺延，统一入口已能完成验证目标。
- 新增技能只能选择已实现的能力，不能通过 manifest 声明“已实现”；遇到新端点、新输入/产物合同须单独补一次能力。
- 停用同步、选中技能失效时保留材料、发送前校验、原初始请求事务及未知提交恢复继续复用；不退回“先建空会话再检查技能”。

## 5. 公众号实例：研究写作能力

来源固定为既有审阅版本 `redfox-data/redfox-community@d2e24f02340a440a73a96aa6ad6a65f681fba89f/skills/wechat-write`；逐文件清单见[已有 manifest](reviews/2026-11-01-wechat-skill-manifest.json)。新版本需重新比较差异，不运行时跟随 main。

### 5.1 必须新增、不能假装复用的接口

精确接口为 `POST /story/api/gzh/search/hotArticleNew`。已有普通公众号搜索和 10W+ 榜单不能代替它。按[公众号方案第4节](wechat-skill-integration-plan.md#4-精确工具与供应商合同)核实 `X-API-Key`、固定 source、业务码、日期边界、返回字段及当前成本；复用现有 Redfox transport、receipt、预算、同步查询 operation，补该端点的真实合同。

新增能力标识及模型工具名由代码拥有：`search-wechat-hot@1`对应`search_wechat_articles`，`analyze-wechat-research@1`对应`analyze_wechat_research`。这一步是**新服务能力适配**，不能算成“新skill零业务代码”的证明；复用证明放在第9节的第二个图片技能。

### 5.2 完整执行路径

> 以下是公众号首版路径。2026-11-05 已在隔离库验收、未部署的[公众号检索修订](assistant-ux-optimization-plan.md#小红书和公众号的检索与空结果)取代本节及 §5.3 中“少量样本直接写、额外扩期另报价”的约定；它不是其他 Skill 的通用篇数要求。

1. 用户选公众号或由综合入口匹配，输入主题及文本材料；一次多选累计最多10份，沿现有所有权和冻结输入机制。
2. 按现有创作报价确认；已有有效父回合自动授权仍可使用。模型加载原写作规则，已有风格材料或明确不提供风格时不重复追问。
3. 提炼关键词与日期，生成热文查询费用卡；确认后创建查询子任务。查询首版逐次人工确认，不能借用小红书自动 search 授权。
4. 以真实查询结果形成可观察的规律摘要、样本引用和应用计划，再生成完整文章并保存。只记录业务分析摘要，不展示模型私有思考。
5. 新建作品必须有当前任务的有效研究和分析。缺检索/零可用样本/分析失败不能保存材料稿冒充研究创作；有可用主题样本但数量不足，直接继续并如实说明范围，不多加一次确认。
6. 复用所选准确稿件版本修改时，可继承其已验证研究；新建不能借旧研究绕过查询。

新增 `wechat-research-writing@1` 交付合同，复用可复用的来源身份校验和保存能力；公众号字段与维度由自己的合同处理。**不把当前 xhs-research.ts 整体改造成大而全分析框架，也不修改小红书 v3 的交付要求。** 后续同类公众号风格技能复用这一合同，不按 skillId 再写分支。

### 5.3 保留的适配与限额

- 不运行原脚本。公众号的扩期条件见上方修订；仍是每个查询子任务最多一次外发，每个任务最多两次实际热文请求，结果未知不盲重发。
- 多关键词合并为一次请求，日期冻结并显示具体范围，不擅改用户关键词或日期。
- 字段缺失记未知；保留真实0；按可靠 URL/id 去重；摘要不声称全文；按已批准方案最多投影10条，保留实际数量及截断说明。
- 文章继续使用 `text-draft`，保留标题、正文、观点、标签、规律、引用及范围说明；不新增公众号富文本编辑器、封面生成或发布。
- 父模型仍用 `modelFor("assistant")`，复用现有每回合上限；不足时明确失败/补充，不偷偷换模型或增加收费回合。
- Redfox 余额不足按业务码在现有后台服务页面提醒；前台只显示友好的服务不可用提示，不执行充值或原脚本的付款恢复流程。明确拒绝与结果未知沿既有人工核对路径处理。

## 6. 图片和视频实例

### 6.1 选定范围

| 样例 | 首版能力及合同 | 验证输入/交付 |
| --- | --- | --- |
| 图片 A（已实现）：`image-generator` | 现有`redfox.image.generate`，固定`gptImage2/1k/单张/no-reference` | 文本提示词 → 独立300积分配置报价 → 人工批准 → 本地图片作品；价格由现有价目读取，不在业务代码硬编码 |
| 图片 B（已实现）：独立外部`claude-image-generation` | 与图片A相同的能力和交付合同 | 只增加固定上游包、binding和注册数据；使用其规则生成一张图片，不增加skillId专用后端分支 |
| 视频（未实施） | 后续按现有能力单独接入 | 本轮没有视频提交、轮询、播放和收费验收 |

图片/视频上游固定版本和文件清单在实施前归档。上游宣称的数量、分辨率、时长、参考素材格式不等于本系统支持范围。例如上游视频文档包含1080p，当前本地 `VideoResolution` 只有480p/720p；上游图片支持10张，现有 GPT-Image-2 本地上限是4张。界面只展示实际可报价组合；超出明确说明，不静默改参数。

会员价格、成本准入和外发开关以实际后端配置为准。现有代码的 `billingUnitVerified:false` 等未核实标识必须查清对应合同后才能做真实试验，不能因截图曾显示价格就自动放行。需要的新价格或成本证明仍应明确批准。

### 6.2 输入与模型边界

- 本轮未新增参考图片输入；助手附件仍为TXT/MD文本，图片技能只接受用户文字需求。未来开放参考图时，须复用私有素材上传、所有权和报价快照机制。
- 未来按文本/图片资产分型后，前端不能把所有附件都当UTF-8解码，报价快照须冻结fileKey、hash和角色；本轮不声称这些能力已实现。
- 不在首版开放上传视频/音频、OCR、任意 URL 下载或自动解析整部视频。后续万相等需要这些输入时再扩展对应能力。
- 文本模型可安排把参考图交给生成接口，不因此声称已经看懂图片。若技能必须先做视觉分析，则必须有已配置、经验证的视觉能力；本轮没有该依赖时将该功能判为不支持，不能凭文件名猜内容。

### 6.3 从费用确认到交付

- 复用 `normalizeToolInput → assertMemberCostEligible → quoteTool`。参数、素材、模型或价格版本变化都重新报价；每次图片/视频生成在会话内明确确认。
- 从现有图片/视频创建函数抽出内部事务版本，旧公开函数保持原签名并调用它。助手在同一事务写入批准、积分预约、子 operation、activation/父回合关联及排队，避免批准成功但关联丢失。不得用反向 HTTP 调自己的会员 API 拼接两次事务。
- 子任务写入现有 `assistantParentTurnId` 归属，父助手进入 `waiting_child`。上传、提交、轮询、下载由既有 Worker 负责；轮询不消耗额外模型回合，也不占着一个长 Python 进程。
- 提交成功必须先持久化供应商 taskId。恢复沿原任务和已保存回执，下载失败只恢复保存步骤；没有 taskId 的未知提交先核对，不能重新生成。
- 收到 taskId 或供应商成功状态不算交付。仅在现有 operation 已保存且校验了实际文件后，建立助手媒体产物引用；记录 resultId/fileKey、turn、activation 和版本，不以临时供应商 URL 当永久作品。
- 助手产物合同增量支持 `image/video`。旧文本 schema 保持；媒体只保存资产引用和说明，预览/下载复用已有组件与所有权 API，不能通过猜 fileKey 读取他人的结果。
- 媒体产物登记采用稳定业务身份，重复子任务通知只登记一次；operation 已完成但助手产物未登记时可补登记，不再次生成或扣费。

## 7. 计费、成本、停止与旧任务保护

### 7.1 一个账本、两类费用

父助手创作费用沿现有 `assistant-turn/assistant` 配置；热文、图片、视频是已有或新增精确服务的工具子单。二者分别展示用途，不能把父创作报价冒充已包含媒体生成。首版不做组合套餐或新的定价引擎。

现有费用自动授权仅涵盖原 turn/search 范围；父回合有效授权仍可用，**新增公众号查询和媒体子单全部人工确认**。UI 在工具卡显示本次费用和必要参数，不新增弹窗或让用户输入另一组授权额度。

积分预约、消费、释放和异常核对继续使用原 charge/run links。媒体子单按原交付事实结算；父助手须新增“该回合要求的媒体已真实交付并形成产物”的交付判据，不能为了结算伪造一篇文本稿，也不能把子单消费重复记到父单。父模型已调用而未完整交付等情况沿现有核对规则，不承诺失败一律免费。

### 7.2 成本归因

每次模型、检索、上传、生成提交和轮询继续经 `paidRequest`、适用服务及会员预算。实际调用事实仍来自 `receipt_attempts`，不是脚本 exit code 或模型声称“调用成功”。

子 operation 继承可信 actor、父 run/turn 和 activation；供应商、端点、模型、价格版本来自规范化和冻结配置。成本中心沿既有链路展示用户/skill/module/服务/模型；多步调用逐项记录，不新增按 skill 汇总一笔的平行账本。相同调用不能因父子展示或多个维度汇总重复计成本；无法精确归属技能的选路模型调用保留现有未分配语义，不伪造归属。

### 7.3 停止、关闭、更新与恢复

| 事件 | 必须行为 |
| --- | --- |
| 管理员关闭技能 | 从新候选和下拉隐藏；已有草稿/材料保留；不取消已接受任务、历史稿件或原费用关系 |
| 已接受父任务等待工具确认时关闭技能 | 继续按其冻结版本和已接受任务政策处理；关闭不等于撤回这个任务，但未批准的工具仍须按原费用规则确认；全局预算/外发禁令继续有效 |
| 发布新技能版本 | 只影响新任务；旧任务使用原包/绑定/能力合同，不覆盖历史行为 |
| 用户停止 | 复用输入框发送/停止切换及现有父子停止；阻止后续未开始步骤，不声称撤销供应商已接受生成或自动退款 |
| 关闭页面/刷新/Worker 重启 | 从持久 operation、任务 ID 和回执恢复；不能重跑整个脚本或用新命令掩盖旧请求 |
| 提交/批准响应丢失 | 沿原 commandKey 查回，不生成新子单；队列和后续草稿沿现有恢复逻辑 |
| 调用结果未知 | 进入原核对状态，保留预算与费用证据；人工核对前不盲重发 |
| 产物文件保存失败 | 沿原生成结果恢复保存，既不重新生成，也不把供应商链接当已完成作品 |

小红书 v1/v2/v3 包、现有工具、查询授权和研究前置规则不迁移。新增绑定表不得覆盖原工具实现。验证须包含原小红书新建、修改、关闭时在途任务、历史稿件及费用/未知恢复；不把“新旧共用底座”写成无需回归。

## 8. 用户界面与后台最小改动

- 保留当前三栏和手机对话/产出切换。右侧容器支持文字、图片和视频，沿用附件卡片、预览、下载和版本信息；不为每个技能新做页面。
- 技能下拉来自同一目录；只显示可选技能，关闭状态的同步和中性提示保持。选不同技能不会自动清空附件；不兼容材料说明原因并由用户调整。
- 生成前展示必要参数：图片数量/尺寸/参考图，视频时长/分辨率/声音/参考图。复用当前工具表单字段，保持折叠详情；用户未指定且影响价格的项先给明确默认建议，不静默升级。
- 执行步骤来自实际事件：“正在查询热文”“已完成规律分析”“等待费用确认”“正在生成图片/视频”“正在保存结果”。供应商没有进度百分比就只显示状态，不编造百分比或私有思考。
- 所有费用确认在会话流；自动刷新、排队和停止仍使用当前入口。媒体操作不增加常驻“刷新状态/停止任务”按钮。
- 后台现有技能页增加兼容结果、依赖、版本及原脚本执行状态的简洁说明，细节折叠；只保留现有启停操作。后台余额提示放原 Redfox 服务区域，设置页继续只负责预算。

### 9.3 历史：含视频和参考素材的拟议次数与预算

本节保留原A/B/C/D整体试验的预算提案与限额控制方法，**不是当前可直接执行的付费清单**。本地实现与桩验收已经完成，当前真实联调范围以§13 M1/M4的A/B/D为准，不包含视频和参考素材上传；沿已有服务配置重算次数、费用上界并取得相应付费授权。此前累计授权模型37次、检索3次、供应商20元是另一轮上限，**不视为本轮可复用余额**；本节拟议金额也不是已有授权。

以下为原含视频范围的拟议上限，仅供后续对应范围核算参考；当前不照表执行。真实主流程每个样例一次，故障注入先用桩完成：

| 项目 | 本轮拟议新增上限 | 说明 |
| --- | --- | --- |
| 助手模型 | 26次 | A≤8，B/C/D各≤6；每回合仍不能超过系统现有限额，不静默补调用 |

真实试验前按实际冻结参数计算上界：模型输入/输出 token 上限×当前模型费率 + 两次热文成本 + 两张图片成本 + 一条视频成本 + 最多上传/轮询成本。未知金额不记0；任何计费单位未核实、金额上界无法覆盖剩余额度，均不得开始对应付费样例。

这些计数不是现有系统天然提供的“本轮套餐”。真实试验按以下方式限制，不新增生产预算系统：

1. 独立联调库和测试账号，只允许这一轮验证进程外发，采集及其他后台付费任务关闭。固定 A→B→C→D 串行执行，每个样例最多一个父回合；每步前后记录 `receipt_attempts` 增量，上传、提交、轮询的技术重试同样占次数，不能只数成功任务。
2. 现有预算计数是最近1分钟/1小时/24小时的滚动窗口，不是自然日，也不是永久的批次额度。选择一次短时间联调，并确保最早一次试验调用尚未移出24小时窗口：开始 A 时将助手模型的24小时调用上限设为已用次数+8；完成核对后，B/C/D各阶段只增加最多6的可用次数，全轮新增不超过26。服务预算与会员预算取更严格者；每回合自身8次硬上限保持，不把它冒充6次限制。
3. 查询、图片提交、视频提交、媒体上传、状态轮询分别绑定现有实际 service 的预算，并核对这些 service 是否恰好覆盖预期 HTTP 类别；设置整轮2/2/1/5/60次的剩余额度。若一次业务内部有额外外发，照实计入，不隐式增加额度；服务映射无法准确约束该类别时先补验证限制再付费，不能仅写人工清单。
4. **现有预算只有次数熔断，没有人民币余额闸。** 本轮金额通过“冻结参数的可信单次费用上界×硬次数上限”限制：按服务计算的总上界必须≤获批总额，且模型输入/输出token和视频时长等计价量有实际服务端限额。不能把成本中心的事后估算当作金额熔断。任何服务无法给出可信费用上界时不运行该付费样例；本轮不另建金额预算平台。每阶段对账时，待决调用按费用上界继续占用，不能当可用余额。
5. 最早调用即将移出24小时窗口时不开始新样例，并提前停止试验 Worker 外发；以后恢复必须按整轮账本计算尚可增加的次数，再把当前窗口已有次数加剩余额度写回预算。不得重建库、重置账本或靠滚动窗口释放计数得到新额度。隔离验证启动/截止控制须先用桩证明会在规定时间停发，不以自然日零点代替实际滚动窗口。

预算不足或出现结果未知立即停在原任务核对，不用新 run、备用模型或再一笔扣费绕过上限。视频生成可能在本地停止后继续，已提交费用按上界保留。轮询用完不代表供应商任务失败，也不能写成成功验收。

真实验收报告分别列：供应商记录/本地估算及其来源、模型 token usage、会员积分预约/实扣/释放、各样例交付、未验证项。拿不到供应商账单时只称“按已确认费率计算的成本”，不写“已核对供应商实扣”。

| 收益基线是否夸大或漏算投入 | §1/§9.4以当前已复用的框架作基线，拆F/G/N/M，人工/AI/等待分列，估算与实测分开，仅用验收记录不建统计系统 |

实施准入结论：可以在以上限定范围内推进；**不能据此声称支持全部 Agent Skills，也不能把“无须改业务代码”写成“无须检查或配置”。** 若 P4 仍须针对 D 写业务分支，则这轮通用目标没有完成，应修正最小绑定边界而不是扩建更多平台功能。

完整草稿另经两路只读复审（契约/计费边界、代码接点/文档一致性）；本次补充再经独立只读复核，已收紧脚本行为覆盖、外部样例完整性和工时可比性。未发现需要另建平台或改写现有小红书的理由。上述是方案阶段结论；后续实现、核心测试和M4真实接口验收的当前结果以§13及[验收记录](reviews/2026-11-02-generic-skill-integration-acceptance.md)为准。

### 14.2 V1：批准卡显示实际执行参数

当前后端已在`assistant/tools.ts`规范化图片请求并生成报价，`execution.ts`把`normalized`保存在工具调用结果；批准时再从该快照执行。前端`turn-cards.tsx`却读取原始`call.input.size`，甚至在缺省时显示`1:1`。问题在读投影和展示，不需要第二个比例解析器。

最小实现：

1. 沿现有会话读取投影，从本次报价绑定的冻结`normalized.commandInput`提取可展示的图片参数，给`AssistantCall`增量提供安全的确认摘要；字段只覆盖实际提示词、比例、清晰度和数量，不返回完整执行载荷、凭据或供应商内部字段。当前会话DTO仍直接返回`c.result`，因此图片调用的公开`result`也要去掉内部`normalized`，保留既有公开完成结果与错误信息；仅增加摘要而仍原样返回内部对象不算完成。此调整限定图片调用的读投影，不重构全部工具合同，也不改后端保存的执行数据。金额、有效期仍使用现有`ToolQuote`。
2. 图片确认卡只展示该摘要，不能以原模型提案或前端默认值冒充实际执行参数；前端不重新解析“竖版海报”等用途词。用户原始消息仍原样保留在会话中。
3. 沿用现有`quoteId`、`proposalRevision`、过期检查和批准命令。当前重报价入口重新准备参数后只更新报价，实施时必须保证二者一致：优先复用已冻结参数更新价格；确需重新准备参数时，将规范化参数与新报价在原事务中一起更新，并按现有修订机制重新确认，不能新报价配旧参数。确认时仍由服务端校验当前提案和报价，不信任前端回传规格。
4. 对没有可靠冻结参数的旧待批准记录，说明“需要重新确认图片规格”，通过已有重新报价入口恢复；不能猜`1:1`或直接批准。已接受、在途或已完成记录保持原任务和参数，不为修展示重新执行。工具完成或拒绝会替换`call.result`，因此已执行历史卡的规格应投影原有子任务保存的`input.parameters`等可信记录；无子任务且无可靠规格时如实说明，不能套用当前规则回算历史规格。复用已有会话读取路径，不逐张卡新增HTTP请求或独立参数表。

验收重点：构造“提案1:1、规范化4:5”这一真实触发条件，确认卡显示4:5，批准后本地桩收到4:5；提示词、数量及清晰度也一致。刷新或恢复后仍展示同一份冻结信息，过期报价不能发起生成。只证明请求参数一致，不能用固定桩图片证明厂商实际出图尺寸。

### 14.3 V2：提前说明收费范围，保持轻量确认

用户路径继续为“确认助手创作费用 → 执行中按需要确认查询或图片费用 → 继续同一任务”。不合并父子收费、不改变价格，也不把每个步骤改成独立收费。

复用`TurnQuoteDialog`，将父卡标题改为“本次创作 {当前报价} 积分”。按2026-11-03用户追加要求，默认提示随本次报价冻结的候选技能能力展示：纯文字不显示额外服务提示；仅支持检索时显示“检索另行计费。”；仅支持图片时显示“图片生成另行计费，生成前会单独确认。”；自动选择等同时允许两类能力时显示“如需检索或生成图片，将另行计费；图片生成前会单独确认。”，不预测本次实际调用。原需求、冻结/核对等较长说明仍留在折叠详情。首条、后续消息和排队费用卡共同复用此处，不各写一套。只保留已有“取消／确认继续”和必要的过期重报价操作，不增加弹窗、金额输入框或新的授权按钮。

子卡保留自己的准确报价，使用“生成图片 {当前报价} 积分”“查询热文 {当前报价} 积分”等业务名称。金额读取已生成报价，不硬编码200/20/300，不在父报价阶段额外查询供应商、预测未来调用次数或拼出不可靠的总价。前端说明要与既有费用模式一致：现有可自动授权的小红书检索继续按原授权执行；公众号查询和图片的人工批准范围不变。默认提示不承诺所有检索都需再点一次确认，完整授权规则沿用已有费用设置说明。助手报价仅增量携带只读展示字段`additionalFeeKinds`，由服务端解析冻结候选的已验证模块工具生成；不新增能力查询接口或独立状态，不进入报价输入身份和授权判断。旧报价缺少该字段时使用中性说明“额外服务费用以执行前的报价为准。”，保留原恢复入口。

取消子操作按既有规则处理已执行的父创作，不承诺整轮免费或自动全退；停止、失败和结果未知沿用现有费用核对。费用模式说明中涉及“额外检索”的范围一并核对，不改变授权额度、钱包和结算实现。

### 14.6 最小验收与完成标准

### 14.7 方案自审

- 核心问题有对应动作：V1解决“确认与执行不一致”，V2解决“收费范围看不见”，V3–V5解决产物和选项不好理解；没有把生成质量归入这一轮界面修订。
- 参数继续以服务端冻结记录为权威，价格继续以原报价为权威；界面不新增参数解析、定价、身份或计费状态。
