## 1. 目标和产品决定

1. 下拉按 **Skill** 展示：自动选择、通用写作、小红书创作、公众号创作、图片生成等；只显示后台已开启且属于当前助手范围的技能。内置验证技能若管理员开启，也按同一规则显示，不设置固定隐藏名单。
2. `xiaohongshu-creator` 仍是一个 Skill。其内部包含 M1 写笔记、M2 改写、此次新增 M4 封面；不注册第二个“小红书封面 Skill”，不新增专属助手窗口。
3. 选中“小红书创作”后，助手根据用户要求选择内部功能，意图确实不清楚才问。欢迎页可保留“写笔记 / 改写文案 / 做封面”快捷按钮；会话中不常驻重复按钮栏。
4. M4 必须完成真实封面研究：**查询爆款 → 筛选参考 → 真正读取封面图片 → 总结视觉规律 → 三套设计方案及提示词**。用户可只保留方案，也可选一套、确认图片费用后生成一张真实图片。
5. 原 M1/M2、公众号及外部图片 Skill 的既有功能、历史任务、计费和恢复继续有效。M4 与外部图片 Skill 共用底层生图能力，不需要 Skill 相互调用。

不包含：M3 标题评分、M5 违禁词检测、自动发布、参考图上传/图生图、人物或商品一致性编辑、批量出图、透明背景、任意脚本执行、Skill 安装器、通用工作流设计器。TXT/MD 累计 10 个附件的入口保持原范围，不因服务器读取参考封面就开放用户上传图片。

### 1.1 流程由 Skill 指令执行，后台只核验必要交付事实

原包通过 SKILL.md/参考规程要求 Agent 按顺序检索、分析和创作；查询脚本负责请求与结果处理，没有一个控制全部写作步骤的程序。选题、选样、规律分析、写作和自检继续由模型遵循 Skill 指令完成，不再把原规程逐步硬编码成另一套固定工作流，也不新增门禁系统或逐步骤审批。

后台只在必要的工具输入及作品保存边界核验事实：研究样本确实来自已完成的查询，引用属于当前任务或明确选定的历史研究，研究交付关联已完成的分析；M4 的视觉观察须来自实际收到图片的视觉调用。复用现有工具与交付检查，不用模型一句“已研究”替代执行记录。这些检查验证记录及归属，不评价分析质量，也不声称能控制模型内部思考或聊天文本的先后顺序。既有权限、费用批准、预算、幂等与恢复校验保持不变。

直接选择 M2 改写不要求研究；已选定经过研究的稿件继续修改，可复用其确切版本的分析，不机械重复查询。已进入 M1 研究创作的任务，不能通过换用 M2 保存普通稿件来冒充研究交付。研究失败时由助手说明情况并暂停，不增加一个由版本号决定是否必须研究的开关。

### 1.3 问题原因与封面接入的防复发约束

2026-11-03补充。以下原因依据已确认代码和测试范围归纳，不推断原开发者动机：专属内容规则混入共用执行层、不同位置的参数/交付定义未对齐、任务生命周期未贯穿查询结果与前端状态，验收又未覆盖这些关键组合。此前主流程通过不足以证明整体接入已收口，不能把这些实现和复核遗漏归因于模型。

封面接入沿三项既有职责实施：Skill负责研究、选样、视觉规律和设计要求；工具能力负责真实查询、图像分析、生成和保存；统一底座负责权限、报价、付款授权、成本、任务状态与恢复。不把这三项再建成新的分层框架。

| 已发生的原因 | 封面接入必须遵守的边界 | 验收落点 |
| --- | --- | --- |

## 3. 用户操作流程

### 3.1 Skill 选择

- 综合入口默认“自动选择技能”，也可手动选择“小红书创作”。输入“把这段话改成小红书风格”走 M2；“研究后写笔记”走 M1；“做一张通勤穿搭封面”走 M4。
- 新欢迎快捷按钮选中所属 Skill、填入可编辑的需求模板并携带现有 taskHint。taskHint 是本次意图，不是权限或付款授权；明确请求改写时不得顺手研究、生图。用户修改需求后以新消息为准，互相矛盾才澄清。
- 专属小红书助手仍使用同一 Skill；下拉不出现三个“小红书技能”。对应功能的可用/暂不可用状态从同一模块目录读取。
- 技能停用后，分组项与其快捷动作一起隐藏。已选草稿保留，温和提示不可用，不自动换 Skill。保留现有 10 秒轮询、回到页面/打开下拉刷新及发送时后端校验。
- 纯 M2 的明确旧动作请求仍只显示改写费用。新 Skill 级范围可包含多种能力，费用说明使用条件句“如需查询参考、分析封面或生成图片，会分别报价”，不能写成每次改写必收这些费用。说明默认轻量一行，细项收进详情，不增加一个付费意图分类请求来提前猜金额。

### 3.2 封面主路径

1. 用户选“小红书创作”，描述主题/用途，或者引用自己的笔记。只缺少会影响检索或设计的关键信息时询问。
2. 沿现有会话费用卡确认父创作报价。该报价包含受限的文本模型组织、规律总结和三套方案；明确说明参考查询、视觉分析、生图另行报价。
3. 展示“查询爆款封面参考”：关键词、明确日期窗口、一次查询积分。确认后执行精确聚合接口，不先收费查询四个不同榜单凑结果。
4. 根据返回标题/内容与用户意图筛选最多 20 个封面来源，展示“分析参考封面”的一次报价，注明最多分析数量。用户确认后，服务器安全取得图片并由视觉模型逐图分析。多个小批次共用本次视觉任务的批准，不要求每张或每批点确认。
5. 展示实际进度，例如“正在读取参考封面”“已分析 10/18 张”“正在整理三套方案”。数量来自持久结果；下载成功不等于已分析，失败有简短说明。
6. 在右侧作品区保存封面研究与三套方案，包含真实参考图、风格规律、每套的文字/布局/配色/提示词。对话里给简短结果和选择入口。
7. 用户选择“只保留方案”，结束本次创作；或选择“生成方案一/二/三”，出现既有图片确认卡，展示选定方案、3:4、1K、1 张、实际积分，确认后生成。
8. 生图成功并保存本地文件后展示“封面图片已生成”，可预览和下载。三个方案不默认生成三张图片。参考图仅用于研究，不自动送入生图接口作为参考图。

手机复用对话/作品标签切换。方案纵向排列，参考图为紧凑缩略图网格，支持点开查看；主操作靠近对应方案，长提示词默认折叠/可复制。费用卡留在会话流，输入框为空时发送键用于停止；有输入时发送排队，现有行为不另做一套。

### 3.3 方案和成图的结束条件

当前执行器遇到成功 `save_draft` 就结束父回合，不能把封面方案硬塞进它后再偷偷继续运行。M4 使用自己的小型交付合同：

- 保存 `xhs-cover-plan` 后，若用户原需求仅要方案，校验后完成；否则进入现有 `waiting_question` 等待选择。选择和报价确认继续原任务，不重复收一次父创作费。
- “生成这版”复用现有回答命令，将方案 ID、精确版本与选择写入当前任务；后台校验为本会话当前待选方案，再准备图片报价。聊天里一句“同意”不能代替图片批准接口。
- “只保留方案”或明确取消尚未执行的图片建议，以方案交付完成父任务；不显示成图成功，不创建图片子单。
- 停止、离开页面、图片结果未知时，不把任务自动当作“只要方案”。按原停止/核对规则保留状态和费用，方案仍可查看。
- 完成/结算后的父任务不再复活。以后再次修改方案属于新需求；以后生成其他方案需要新报价，并在提交前展示是否还包含新一轮创作费用，不暗中复用已消费报价。

该分支只属于 `xhs-cover-delivery@1`；普通写作和独立图片任务继续原完成规则，不扩成任意多阶段工作流引擎。

当前回答接口只有 questionId、expectedRevision、answer 文本；实施需在原合同增加可选的严格结构化封面选择，并在原 pending_question 中关联方案版本。按钮选择必须匹配当前 questionId、turn、所属会话与作品版本；相同选择重复提交幂等，不同选择或旧按钮产生冲突并刷新。普通文字回答继续原方式，不能从自由文本提取一个 ID 就把它当作可信选择或付款授权。自然语言选择最终形成的图片建议仍须展示确切方案和报价供用户确认。

## 4. 选择合同、目录与历史兼容

### 4.1 最小协议扩展

现有 actions 增加 `skillId/skillName`（由 binding 计算，不由前端命名）；下拉将 actions 按 skillId 分组，快捷按钮仍使用模块动作。分组名称来自 Skill，分组可用性为其功能至少一项可用，不新增可见性配置或第二个目录表。

新 `skillSelection` 严格支持以下形状，互斥且拒绝未知字段：

| 请求 | 意义 |
| --- | --- |
| null/省略 | 当前助手范围内自动选择 |
| `{skillId:"xiaohongshu-creator"}` | 只可选择该 Skill 在当前 profile 已接入的模块 |
| `{actionId:"xiaohongshu-rewrite"}` | 旧请求/恢复兼容，仍严格限定原 M2，不升级为整个 Skill |

新界面正常选择和快捷入口发送 `{skillId}`；旧未决命令按 `{actionId}` 原样重放。恢复的旧精确动作在界面轻量标注“本次：改写”等；用户主动重新选择 Skill 才解除旧的精确模块选择，并重新取新任务报价。切换下一轮的选择不能改变已发送请求。

后端在 initialRequest、quote/submit、enqueue、重报价、scope 校验与执行规则中使用同一选择解析。系统指令同步区分“选择 Skill 可在其内选功能”和“旧精确动作不可换模块”。客户端不能指定包版本、工具、供应商或任意 moduleId。

新快捷入口的 taskHint 必须同步补进首次创建的 initialRequest、前端请求类型、pendingCreate/报价/排队/未知提交的恢复白名单，并随命令原样冻结；旧记录不含 taskHint 仍合法。用户改动未发送的需求时，清除或更新对应提示；不得让旧快捷动作压过用户后来编辑的明确文字。

### 4.2 不扩大旧任务权限

- 发布 `xiaohongshu-creator` v4（建议新目录 `xiaohongshu-creator-v4`），保留 v3/v2 文件及原 hash；registry 只切换新任务的 currentVersion。
- 在 S0 清理 tools.ts 中写死 `xiaohongshu-creator / M1 / version='3'` 的联合条件，不只替换版本号或追加身份列表，不以发布封面版本为清理前提。该条件目前仅用于防止已选研究模块后换用无研究模块交稿；M1 自身的研究真实性检查已经按其声明的分析工具触发，不是所有研究检查都绑定了版本 3。统一依据已冻结模块的研究能力及交付要求判断，优先复用已有工具声明与交付逻辑，不新增策略开关或控制层。具体问题、处置和验收统一见§1.2。
- 保留旧包和快照只为历史任务恢复，不是保留版本特判。旧 v2 仍按原冻结合同处理，包括其原有 partial 交付语义；不能清理特判时给历史任务追加新分析要求。旧 v3 和新的 v4 按各自冻结模块的研究声明执行，新任务仅选择 registry 当前版本。
- 不修改已有 turn、quote、queue 的候选快照，不将 M4 追加到旧 M1/M2。旧 actionId、幂等 hash、价格快照、自动授权照旧解释。
- 前端草稿、pendingCreate/pendingQuote/pendingTurn/pendingQueue、初次创建恢复均读取两种选择形状；响应未知时重放原请求，不把 actionId 转为 skillId。
- `additionalFeeKinds` 扩为 search/image/vision 的有限、无重复、最多三项集合；同步恢复记录的枚举和长度校验，旧缺省元数据及旧两项报价继续合法。只调整显示合同，不改变原报价金额或候选权限。
- 历史 v3 包资源仍可解析；当前 skillId 启停开关沿用同一 settings 行，不创建“封面开关”或“只在后台”标记。
- 数据库约束扩展采用新迁移，编号在实施时取实际下一号；不改已应用迁移、不重写历史作品。新类型启用后，回滚先撤销新任务入口并保留能读新数据/旧任务的代码，不把“回到旧二进制”当作安全回滚。

### 4.3 健康状态与运营启停

整个包完整性、账号及公共模型条件失败仍按原规则拒绝。管理员允许新任务时，只要求至少一项已实现功能可用；后台展开显示各功能不可用原因。例如写作、改写正常但视觉服务未配时，可开启小红书，封面标记暂不可用。

运营权限候选与瞬时预算/供应商健康分开：候选权限仍按已发布模块、profile、选择范围和 acceptingNew 冻结；可用性是显示与实际执行的校验，不将每次预算波动写进报价身份，使旧报价无故失效。报价/执行时检查相关功能自身依赖；明确封面请求遇到缺依赖时说明缺口，不改走材料写作。旧 `{actionId}` 精确模块请求可在受理前直接阻断；新 Skill 级/自动请求在模型判明功能后仍受同样校验，不能保证自然语言意图在零模型调用下被准确识别。

M4 的核心交付是研究和方案，生图是可选后续。其交付合同须区分必需查询/视觉依赖与可选生图依赖：只有图片服务故障时，仍可研究并交付方案，生成按钮显示暂不可用；不能因为 manifest 允许 generate_image 就把图片服务算作产出方案的硬前置。只为本次明确的交付合同补该区分，不新增通用依赖表达式或模块开关。

新封面阶段不为所有技能加模型能力评分器或自动降级机制；依赖模型的已有配置项和一项新增视觉用途即可。

| 关键词 | 按需求提炼，至多 5 个去重关键词、英文逗号合并，规范化后总长至多 30 个 UTF-16 单元（逗号计入，补充平面字符如部分 emoji 计 2）；一次 HTTP，不按词循环。首批不开放空关键词全站查询。原脚本仍标 200 字符，此处按 2026-11-03 真实接口边界修正，详见费用体验方案 §11.8 |
| 日期 | 默认近 30 天、T+1；复用北京时间日期帮助函数，冻结并显示日期窗口。原 API 只有 startDate，不能给它附加自造的 endDate 并宣称查询严格支持任意截止日；需更窄窗口时对有可靠发布时间的记录本地过滤，并披露实际供应商范围 |
| 响应 | 四个数组：lowPowderExplosiveArticle、likeTheTop500、singleDayIncrements、sevenDaysOfIncrements；合法空数组与缺字段/错误响应区分 |

| 次数 | 每次封面研究默认 1 次查询；不复制原脚本最多 3 次自动重试。不自动换词、扩期、翻页、补足 20 张或替换其他榜单 |

须在真实联调前核实当前接口方法、鉴权、source 接受情况、日期窗口、响应 schema、供应商成本及会员价；静态脚本不足以证明当前线上合同。缺成本或价格时禁止付费外发，只完成本地桩验证，不借 M1 的 20 积分价兜底。

规范候选取供应商每类前20个有效去重来源，合并最多80个候选，补全跨榜单归属；统计原始、无效及全局去重数量，明确标注候选截断。父模型摘要整体不超过12000字符，不传无助于文字选样的CDN图片地址；图像能力按来源身份从持久结果取原地址。原始回执仍受4MiB响应上限约束并按原机制保留。结果按真实笔记 ID/可靠 URL 去重，保留其所属四类标签；缺失作者、互动等为未知，真实 0 保留 0。保存 photoId、userId、标题、作者、真实 coverUrl、笔记 URL、时间、可用互动字段及缺失说明。无真实来源身份/图片地址的条目不冒充可分析封面。

以主题相关性优先、数据表现辅助，从候选元数据中选最多 20 张。保留原规程的四维选样意图及参考权重，模型给出简短可观察的选择理由；不开发新的打分服务，也不将模型分数包装成客观流量预测。原规程“相关性优先”与后段“仅按互动排序”有冲突，本次明确以前者为主，互动只用于相关样本间排序。

数量不足时用实际可用样本分析，报告分母为真实成功数；零可分析图片时暂停，不根据标题猜配色/构图。主题不同或用户明确要求新研究时才重新报价查询；修改同一已选方案可复用该确切版本的研究证据，不能凭手工粘贴链接冒充已有研究。

## 6. 真实视觉分析：复用模型与任务设施

### 6.1 实现边界

新增功能内 `analyze-xhs-cover-images@1` / `analyze_xhs_covers`，由单个视觉子 operation 承担安全取图、有限批次看图、逐图记录和结果交付。它不是由文字模型直接写一份“已看图”分析；视觉调用确实接收图片内容。

在现有模型管理 CAPABILITIES 中增加“封面图像分析”用途，选择已注册且有 vision 能力的模型，优先复用现有凭据和端点。`qwen3-vl-flash` 只是代码中已有候选，不宣称目标环境已配置或本轮已验证。型号、端点、非敏感参数、能力、价格和限额随视觉任务冻结；配置变更不偷偷换模型。

不能直接调用当前 `chatJson` 当完整助手步骤：它没有 operation 的 beforeClaim/onReceipt。视觉适配只在 assistant 功能内补受控请求边界，复用 MODELS/模型选择、paidRequest、receiptOptions、使用量和价格计算，不改现有新闻分析的调用语义。保留原始 HTTP 响应后解析，并继承会员身份、父任务、activationId、generation、停止和预算校验。

预算使用一个明确的 `assistant.vision` 服务及会员子预算，成本定价仍引用实际模型的 provider/model 价目。不自动开启预算、不把它塞进文本 200 积分对应的 8 次调用额度。

视觉子任务使用明确的 operationKey（如 `assistant.coverVision`）。当前执行分发和“两回合”并发统计按 `provider=assistant` 判断，接入时须按 operationKey 区分：父回合仍为 `assistant.turn`，视觉子任务交给局部视觉执行器，不占另一场父回合名额。将新 operation 登记到现有恢复白名单，停止、代次和恢复沿原父子关联处理；不新增队列或另一个 provider 系统。服务预算标识、operationKey 与实际模型供应商分别承担原有职责，不能混为一个字段。

### 6.2 图片、批次和逐图证据

- 只接受本次合法查询结果中已选择的 sourceId；模型不能指定任意下载 URL。复用 `produceImage/guardedFetch` 的安全取图与变换；视觉边界再验证 JPEG/PNG/WebP、像素、单图字节及批次总量，不直接接受 SVG/动图透传。
- 初始安全规格沿用取回 15 MiB/20 秒上限；视觉处理目标长边不超过 1200 像素、每张编码不超过 1 MiB、每批不超过 5 MiB（实际模型限制更严时取更严者），解码像素限制继续用已有安全校验。编码尺寸不能代替文字可读性验收；无法看清应如实标明，不凭猜测填字。
- 图片经过固定处理后以私有任务资产冻结其内容/hash。批次记录图片 ID/hash、来源、预处理版本；恢复使用原内容，不重新下载会变化的 URL 来复用旧回执。参考资产不伪装成用户生成作品。
- 初始实现目标为最多 20 张、每批最多 5 张、最多 4 次视觉 HTTP；串行保存每批结果，不新增并行任务调度器。是否能在该批次内清晰识别封面文字，须用实际模型合同和本地/获准真实样本验证；无法满足时先修订限额和报价，不悄悄多发请求。
- 逐张分析不等于逐张发 HTTP。每张都返回 sourceId、可读文字、场景/主体、色调、构图/排版、缺失或不可判定项；同批图像间不得串 ID。文本模型只拿结构化观察和必要缩略引用，不能拿 URL 字符串当视觉结果。
- 不把图片 base64 送入现有 `contextTokens(JSON.stringify(...))` 当普通文字计算。视觉请求分别限制文本、图片数量、尺寸及字节，按选定模型合同计算/保守约束图像输入；无 usage 时成本标未知/估算，不虚报零。
- 取图失败、解码失败、模型未能看清、调用失败分别记录。只有实际收到并校验图像观察的条目计入“已分析”。有可用样本可按真实范围继续，三套设计可有创意差异，但不得宣称三种风格都在样本中出现。
- 停止后不再提交下一批；已完成批次和收到的回执保留，未知批次不自动重发。解析失败先重解析保存响应，不重新买一次模型结果。

### 6.3 上限与恢复

父文本模型的上下文也必须有整体预算：系统说明、工具定义、实际激活的Skill规程、已接纳用户材料、查询摘要、最多20张图片的结构化观察、必要对话/工具记录和方案生成所需余量一起计算。逐批限制图片数量或字节不能代替这项约束；同时遵守冻结模型的输入上限、输出上限及总上下文限制（模型合同存在该项时），不通过临时换模型或提高全局额度兜底。

沿现有结果投影实现有界摘要，限制进入父模型的查询正文和逐图描述，避免把原始视觉响应和同一份完整观察在后续消息中重复注入；保留每张sourceId、实际分析状态、必要观察和截断说明。原始结果仍持久保存，不能为节省上下文删除恢复证据。输入接纳时预留完成该交付所需空间；先缩减可裁剪的工具结果正文和观察描述，不能悄悄删掉用户材料、工具参数约束、权限/付款说明或必要Skill规程。若现有限额内无法容纳已承诺的20图主路径，应修订投影/输入边界并验证后再启用，不等用户买完查询才用“缩小材料”结束任务，也不引入自动付费摘要或新的上下文管理服务。

继续保留父文本模型最多 8 次、子外发最多 20 次的现有限额。正常最多 1 次检索＋4 次视觉＋1 次生图提交，最多还剩 14 次图片轮询；不为 M4 静默增加全局上限。按真实外发计数，复用回执不重复计数。剩余额度不足不重建任务或重新提交图片；保留供应商 taskId 进入既有核对流程。

到达限额与“模型仍可继续编造方案”不是同一回事；未交付就明确未完成。本地桩必须证明目标 20 图和正常成图路径可在上限内运行；真实模型如需更多轮，先调整方案/预算并获准后再测，不循环到成功为止。

## 7. 方案作品与生成图片

新增 `xhs-cover-plan` 使用既有 artifact_versions 表、CAS 版本、会话所有权、作品列表和来源快照，不新建封面业务表。结构最少包括：

- 主题/目标与研究窗口，查询/分析工具身份；候选、选择、下载、分析成功数及失败说明。
- 基于成功图片的风格总结与真实来源缩略引用。
- 恰好三套可选择方案：稳定方案 ID、名称、画面与文字布局、配色、参考 sourceIds、可执行生图提示词、目标比例 3:4。
- 服务端验证的研究身份、逐图观察摘要及范围标记；用户手动编辑内容不能伪造已验证来源。

用 `save_xhs_cover_plan` 及 `xhs-cover-delivery@1` 校验查询→视觉证据→方案的依赖，不能只用普通 text-draft 冒充。展示支持复制提示词和引用后继续修改；首版不新增画布/排版器/复杂表单编辑器。

生成时沿用现有 `generate_image`，增加可选的、由服务端验证的方案引用（artifactId、version、schemeId）；对于冻结为`xhs-cover-delivery@1`的激活，该引用及有效研究是必需条件。此处不能实现成按`skillId=小红书 / moduleId=M4 / version=4`判断，模块身份只用于选择、来源与成本归属。独立图片Skill按原交付合同执行，不被附加封面研究要求。冻结实际提示词、尺寸、数量与方案版本，不在用户确认后自动改方案。

目录沿现有有限合同校验封面交付必需的查询、视觉分析、方案保存能力及`xhs-cover-plan`输出是否一致；能力声明缺失时在新任务准入前拒绝。`generate_image`为可选后续：未绑定或服务暂不可用时仍可交付方案，但不可提供可执行的生图入口；绑定了能力也不能跳过其报价和批准。不要用同名deliveryContract字符串代替能力与交付证据检查，也不建立可配置规则表达式。

M4 的设计目标为 1080×1440，但当前生图只承诺 **3:4、1K、单张**，以供应商真实结果展示像素。不为了表面吻合而偷偷拉伸、裁图；精确 1080×1440 输出和参考图生图后置。原包“上传自己的图片结合方案生成”的末尾指引改成当前可用的“选择方案生成一张图片”，并在适配说明记录该范围差异。

研究原图不无限保存。复用原资产表、私有访问和清理器，增加明确的参考资产 origin（如 `assistant-cover-reference`），首版期限固定为创建后 30 天，不增加后台期限配置。现有到期访问/清理只覆盖 `subscription-video`，不能直接假定新参考图已受相同规则管理。

清理前检查原父子关联：父任务仍等待选择、可继续执行或仍有未解决的未知/核对状态时，恢复所需源图和查询/分析结果受保护。现有 operation_results 的 30 天回收也须识别这类引用，不能因视觉子任务已完成就清掉尚待父任务使用的分析。父任务已结束且必要证据完整冻结到方案后，过期参考资产和可回收子结果才可释放；未形成作品但需继续核对的任务保留所需证据至核对结束，不设一个独立任务到期状态机。

方案保留服务端验证的来源、hash、观察与分析范围快照。参考缩略图到期显示不可用及原文链接，不重新外呼或破坏已保存方案；生成的用户作品沿原保留和删除机制。不能只把临时缓存路径放进历史作品，也不能依赖已过期 operation_results 才能读取历史设计方案。

## 8. 报价、自动授权、结算与成本中心

> 2026-11-03后续费用决定：用户已确认“一次任务、一次费用确认，先冻结上限，结束/停止后按实际结算”，以[统一任务费用方案](assistant-fee-experience-revision-plan.md)为后续实现权威。原目标已含生图时选方案后不再二次确认。下表及本文件既有验收记录描述当前逐项计费实现，未随本轮文档修订改代码；新费用方案尚未实施。

合计按 `父创作价 + 查询价 + 视觉分析价 + 可选一张图片价` 展示；100 积分 = 1 元仅为会员标价换算，供应商成本单独统计。两项新价确认前，不给出一个虚构的“完整封面总价”。

固定视觉任务报价应在详情说明“分析最多 N 张参考，实际读取失败会在结果中注明；本项按任务计费”。取图失败造成样本减少、但所有已发送视觉批次有明确有效结果时，可交付标明范围的分析报告；至少一张成功且有真实可观察信息才可作为 M4 研究依据。技术失败、解析未完成、未知回执、全零可分析样本不能按成功报告结算。这里不新增按张退款算法；异常/部分技术结果进入既有 review，由原核对机制决定结算，不承诺失败全部免费。

视觉交付新增一个明确的结算证据类型，只有验证后的分析报告才满足 `assistant-vision`，下载进度或任意 genericResult 不算完成。父创作只有持久方案/成图通过合同验证才有 assistant_delivery；图片费用仍以真实图片文件为证据，文字方案不能结算成图。

已有自动授权保持原边界：父创作可按原价目授权自动确认；旧 allowSearch 仅涵盖原笔记检索。**封面聚合查询、视觉分析、生图首批均逐项人工确认**，不能因为属于同一小红书 Skill 就继承旧检索授权。每项确认都在会话流中，轻量显示金额和动作，详情折叠；不新增授权总面板。

费用说明的类型增加 vision，来自冻结候选的能力；只说“可能使用”，不因选择包含 M4 的 Skill 直接预占所有子费用。尚未发生的子调用不收取；更换方案/参数需新的匹配报价与明确批准。

成本中心复用原回执、operation、assistant_tool_calls.activationId 链路。查询、每批视觉、图片提交/轮询都归到原用户、会话、Skill=`xiaohongshu-creator`、module=`M4`、冻结版本及实际供应商/接口/模型；首次选择功能前的文本请求仍按真实候选范围标注，不能事后伪造单模块归属。新增服务登记和 usage/价格解析即可，不新增成本表或统计系统。供应商余额不足继续仅在后台服务页给运营提示，用户看到可理解的暂不可用状态。
