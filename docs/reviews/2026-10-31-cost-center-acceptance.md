日期：2026-10-31。分支：`codex/assistant-v1`。同步基线：`5355678`。状态：经 `kimi-code-cn/k3.1-pro-highspeed` 复审、修复并复验后通过；未提交、未推送、未部署。

本轮按用户要求由监督式开发流程推进，复用现有后台组件、供应商回执、模型身份、Skill 激活、万相任务费用、预算和会员积分机制。验证只使用本地桩、隔离测试库和合成数据，没有调用真实付费供应商接口。

## 1. 范围与交付

新增后台独立入口 `/admin/costs`，包含“概览”“调用明细”“已存账单”：

- 可按北京时间、计费供应商、接口服务、operation、模型、Skill、模块、用户、执行者、来源、环境、状态和费用依据筛选。
- 支持按供应商、接口服务、模型、Skill、用户汇总；可从汇总进入同条件明细。
- 金额只在 `origin + environment + currency + costBasis` 相同的桶内求和，不跨执行环境、币种或费用依据相加。
- 已存 Redfox 账单继续使用现有接口、解析和限制说明，不混入调用费用合计。
- 设置页继续负责调用预算与预算池，只增加成本中心入口；模型页继续负责模型配置、质量、延迟和 tokens。

## 2. 数据与计费边界

`receipt_attempts` 仍是每次外发尝试的唯一事实源，没有新增第二套调用流水或费用事件表。迁移只增加统计身份、任务/用户归属、环境、价格快照和 Skill 激活关系：

- `billingProvider` 表示实际向本系统计费的一方；`upstreamProvider` 只记录已有证据证明的路由上游。
- `operationId` 与 `modelId` 分开。旧 `service`、`model`、逻辑键和价目键不改义，已有回执恢复与幂等行为保持兼容。
- 普通查询不把 operation ID 冒充模型；模型接口可同时记录 operation 和 model。
- Jina、SocialData、Dajiala 只有官方端点证据才确定供应商；自定义代理保持“身份未知”。AgentKey 的已验证路由上游可在明细中显示，但不同上游混在一组时不擅自变成一个新的供应商分组。
- 新调用的用户和任务归属在外发时冻结；历史无法唯一确认的归属标为未知或未归属，不用当前关联补造历史事实。
- 一个模型步骤可有多个激活的 Skill/模块。共享步骤只计一次并标记“不可按单个 Skill 相加”；历史步骤与确认未激活分开表达。
- 万相费用锚定提交任务并只计一次；窗口内发现任务身份后，会回查同一 `provider + configIdentity + taskId` 的全部提交证据，因此跨日分段报表与整段报表口径一致。轮询记录保留证据但不重复计费；终态用量或价格冲突时保持未知。

预算、会员积分、报价、预约、消费、释放和退款继续使用原账本与结算逻辑。成本中心 GET 请求只读，不会写预算或积分；币种、供应商 credits、会员积分和 CNY 不互相折算。

## 4. 并发、取消与业务写入影响

- 每个 API 进程最多允许 2 个成本读取，超出时快速返回 503 和 `Retry-After`；事务默认 5 秒语句超时、8 秒事务超时。小连接池降为 1 个读取名额。
- API 已监听请求 `aborted` 和响应 `close`，取消信号传入 PostgreSQL 查询。两个客户端同时断开后，约 29.9 ms 内活动 SQL 释放；随后一个短查询在 155 ms 内返回 200。
- 取消后的连接会回滚并归还并发槽；同一事务上的迟到查询会被拒绝，不会继续消耗数据库。
- 固定 5 路并发执行既有回执落库、预算检查和积分预约/消费/释放，两轮各 250 次。叠加两个大范围成本查询时，写入 p95 从 0.9 ms 变为 0.8 ms，处于噪声范围。
- 本轮并发验证无超时、死锁或重复扣分；510 条 receipt/attempt 写入数量完全一致，积分账本未变。

## 5. 百万行性能验收

主基准为隔离数据库 `aihot_cost_perf_test`，100 万条 attempt，覆盖 180 天，其中近 92 天 505,595 条。环境为 Node.js 24.22.1、PostgreSQL 17.9、Apple M4、10 逻辑核、16 GB、应用连接池 10。每个场景预热后采样 50 次。

| 场景 | 结构化基准 p95 | 验收目标 | 结果 |
| --- | ---: | ---: | --- |
| 7 天概览 + 供应商分组 | 132.1 ms | ≤ 1,000 ms | 通过 |
| 92 天概览 + 供应商分组 | 2,110.8 ms | ≤ 3,000 ms | 通过 |
| 7 天明细首屏 | 32.1 ms | ≤ 1,000 ms | 通过 |
| 92 天明细分页 | 459.0 ms | ≤ 3,000 ms | 通过 |
| 92 天用户筛选 | 354.1 ms | ≤ 3,000 ms | 通过 |
| 92 天 Skill 筛选 | 1,419.5 ms | ≤ 3,000 ms | 通过 |
| 92 天概览双并发 | 2,290.4 ms | ≤ 3,000 ms | 通过 |

查询数量和结果统计不随每页行数逐行增加。概览只计算当前分组；明细翻页不重复计算全范围总额；进入单个 Skill 时复用收窄后的 model links。`EXPLAIN (ANALYZE, BUFFERS)` 已检查，92 天概览、概览元信息和明细页执行时间分别为 1,525.2 ms、572.8 ms、400.1 ms，全部正常读取场景无超时或被并发保护拒绝的样本。

跨账期证据补全使用仅覆盖 `aliyun.wan.poll` 的局部表达式索引，不扫描全部历史 attempt。双并发 p95 为 2,290.4 ms，距离 3,000 ms 目标约 709.6 ms；同一数据规模和采样标准的 20 次短复测 p95 为 2,344.9 ms，结果稳定。结构化基准证据在 `/private/tmp/cost-query-benchmark-highspeed-final-rerun.json`，查询计划在 `/private/tmp/cost-query-plan-highspeed-final-rerun.json`。

## 7. High Speed 复审闭环

用户指定的 `kimi-code-cn/k3.1-pro-highspeed` 首轮复审结论为“不通过”：0 个 P0、3 个 P1、3 个 P2。完成首轮修复后，同一 High Speed 模型做整段/分段反例复核，又发现 1 个跨账期 P1；该问题也已在最终签核前修复。各项闭环如下：

| 优先级 | 原问题 | 修复与证据 |
| --- | --- | --- |
| P1 | 同一万相任务被不同提交关联时可能重复形成费用 | `admin/costs.ts` 以 `provider + configIdentity + taskId` 聚合任务，费用锚定最早提交；后续提交和轮询保留明细但标记费用不适用。跨提交冲突与“同一 taskId、不同 configIdentity 分开计费”均有集成测试 |
| P1（二轮复核新增） | 同一任务的两条提交跨报表日期时，整段查询能判冲突，但逐日查询可能各形成一笔已知费用 | 从窗口内任务身份回查全时段同任务提交证据，并增加万相任务身份局部索引；回归同时跑整段、较早提交日和较晚提交日，较晚提交不新增费用，任何分段都不产生金额 |
| P1 | DeepSeek 峰谷价格没有进入首轮计价 | `providers/deepseek-pricing.ts` 在上海时区决定峰时/闲时，把倍率、规则版本、节假日来源和保守标记冻结进 `price_snapshot`；普通模型与助手模型路径均接入，自定义代理不按模型名推断 DeepSeek |
| P1 | 历史普通任务没有恢复唯一用户或运行归属 | 统一读模型从直接 run 和 `operation_results → run` 恢复唯一 member/Admin/system；多个不同候选保持未归属，不把同一费用复制给多个用户 |
| P2 | 旧 Redfox 本地费用仍使用第二套聚合 SQL | 旧接口保留返回结构，但 `local` 分组改由统一 CTE 生成；账单、本地分组和万相复用同一只读事务，不额外占连接或并发名额 |
| P2 | 缺少缓存拆分时无法说明估算口径 | 明细 DTO 增加 `estimateBasis`，标准输入价且无缓存拆分时明确显示“标准输入价估算，不含缓存优惠”；缓存拆分和固定单价分别标识 |
| P2 | 成本 API 有不可达的重复 busy 判断 | 删除重复的 `instanceof CostCenterBusyError` 分支，只保留 PostgreSQL 超时/锁错误码处理 |

过度设计复核采用“不新增第二套账本、价格引擎、定时任务或前端框架”的边界：分时价格只作为官方 DeepSeek 的局部选价函数，结果写回既有价格快照；历史归属复用现有 run/receipt/assistant 关系；跨账期去重复用同一读模型，只增加服务于精确身份查询的万相局部索引；旧账单兼容只调整读模型接线；缓存口径只增加 DTO 字段，不新增数据库列。本轮没有引入会话、Skill 或工具执行抽象。

同一 `kimi-code-cn/k3.1-pro-highspeed` 完成最终独立签核：**通过，0 个 P0、0 个 P1、0 个 P2**。复审另行构造了跨 92 天分段反例，确认整段与逐段口径一致；修复限定于统一读模型回查、提交身份转换守卫和万相局部索引，未发现过度设计。复审自身的定向回归 38/38、Web 2/2、全仓类型检查和 `git diff --check` 均通过。

## 8. 约束、残余风险与发布状态

- 性能数字来自隔离本地百万行合成库，不是生产数据或生产网络条件下的实测；上线前仍应在接近生产的容量、缓存和并发下复测。
- 92 天双并发 p95 本轮为 2,290.4 ms，距离目标约 709.6 ms；首批未预热测试曾因冷缓存瞬时超过阈值，不能把一次正式 50 次采样结果外推为生产容量保证，上线前仍需按实际数据倾斜、缓存命中、API 进程数和连接池复测。
- 收窄后再做 receipt 去重的查询计划曾观察到约 57 MB 和 45 MB 的哈希聚合内存，本轮概览分组计划还产生 33,145 个 temp read blocks 和 20,447 个 temp written blocks；未采样整个 API 进程峰值 RSS。事务 `work_mem=64MB`，没有为提高速度继续放大连接池或内存。
- 页面截图覆盖代表状态和主要桌面/手机宽度，未穷举所有主题、浏览器和窗口组合。
- 成本中心首版只展示本地证据，不自动拉供应商账单、不计算毛利、不做金额熔断，也不能把 estimated 或余额差宣称为逐笔实收。
- 系统默认 Node.js 为 22.22.2，低于仓库要求的 24.11。本轮最终数据库回归和性能基准通过 Node.js 24.22.1 执行；全仓类型检查、Web 成本页测试和生产构建通过 Node.js 24.21.0 执行，以避开另一个 Node 24 运行时无法加载已签名原生前端模块的环境冲突。
- 独立复审由用户指定的 `kimi-code-cn/k3.1-pro-highspeed` 执行。原结论为“不通过”（0 P0、3 P1、3 P2），修复后由同一模型做最终签核。
- 工作树还包含此前已存在、未提交的助手与业务改动；本轮保留这些改动，没有 Git 提交、推送、合并、迁移生产库、真实供应商调用或部署。

结论：统一成本中心首版已按批准的边界完成本地功能、计费隔离、并发取消、业务写入影响、百万行性能和桌面/手机页面验收。High Speed 两轮复审提出的万相重复计费（含跨账期）、DeepSeek 分时价、历史归属恢复及三个 P2 均已修复；生产性能和正式发布仍需在上线前环境另行确认。
