## 1. 主要发现

优先级含义：P1 为优先修复的可信边界或恢复闭环问题；P2 为有具体触发条件的正确性、运营或验证缺陷；P3 为较低影响的健壮性问题。未发现可据现有证据认定的 P0，这不构成安全认证。

### R1 · P1 · unknown 回执放行后，真实分析任务不会随之恢复

- 位置：`packages/backend/src/admin/runs.ts:91`；实际调用见 `packages/backend/src/editorial/analyze.ts:199`、`:226`、`:248`、`:269`、`:313`；失败状态见 `packages/backend/src/jobs/content.ts:123`。
- 原因：release 只有在 purpose 为 `analyze_article` 时才从 subject 提取文章并重入队；实际分阶段 purpose 是 `prefilter_article`、`score_article`、`structure_article`、`understand_article`、`summarize_article`。
- 触发：模型请求结果未知，文章被标记 failed；超过 30 分钟自动放行，或管理员人工放行同一回执。
- 影响：回执已变 failed，但文章仍 failed、没有恢复任务。五分钟 sweep 只捞 new 状态，不能补救；需要另做文章重新处理。后台显示“已放行”不等于恢复完成。
- 证据：独立测试库使用真实 paidRequest 创建模拟丢响应的 prefilter 回执，老化 31 分钟后执行 `autoReleaseUnknownReceipts()`，结果为 `receipt=failed, article=failed`。
- 建议：按实际工作流所有权恢复，而不是保留过期 purpose 字符串；共同需要成功的状态恢复和入队应原子化。保留一次自动放行与再次 unknown 人工核对的成本边界。
- 缺失测试：从真实文章分析 unknown → 放行 → 重入队 → 成功提交的链路，包含各阶段、重复放行、旧修订与入队失败；只断言回执状态不足。

### R2 · P1 · ingest 可以借用任意已有信源 ID，绕过新外部来源的隔离语义

- 位置：`packages/backend/src/ingest/items.ts:33`、`:56`、`:67`；HTTP 入口鉴权见 `apps/api/src/routes/ingest.ts:12`、`:35`。
- 原因：INSERT 新来源时设 external/T2/isolated，但已有 ID 冲突只更新 last_ok_at，未验证 kind、归属、enabled 或允许的上报入口，随后直接按该来源写材料并入队。
- 前提：调用者持有有效 ingest bearer token，并知道或选中已有 sourceId。不是匿名绕过认证；风险在于专用上报权限被扩大为已有可信信源的材料写入权。
- 影响：第三方输入可挂在已有 RSS/T1/editorial 来源下，继承其筛选上下文和信源属性，进入既有处理链路；即使该来源已暂停也能入队。是否最终公开仍受分析和发布规则限制，本轮不声称已绕过全部发布门禁。
- 证据：独立库创建 disabled 的 RSS/T1/editorial 来源，用该 ID 调 `ingestItems`，返回 created=1，来源属性保持不变且 `processing_queued_at` 已设置。
- 建议：先明确令牌的信任范围；至少限制已有来源为获准 external 来源，并绑定可写 sourceId，拒绝跨 kind/越权及暂停后的新写入。未知来源继续先隔离。不要把“改 sourceId 前缀”当作权限校验。
- 缺失测试：有令牌但非管理员、跨来源 ID、已有非 external、暂停/隔离来源、新来源与重放输入。

### R3 · P1 · 来源隔离后，热榜重算仍保留其公开参与者与热度贡献

- 位置：`packages/backend/src/events/hot.ts:60`、`:108`，`packages/backend/src/events/hot-read.ts:82`；公开返回见 `packages/backend/src/publication/stories.ts:256`、`:289`。文章撤回逻辑在 `packages/backend/src/publication/publish.ts:185`。
- 原因：文章投影按 isolated 撤回，但 heatRows 和 participants 从 story_signals 聚合时不检查来源当前参与模式；头像补充查询也没有对应过滤。
- 触发：同一 story 曾有至少两个参与来源，其中一个改成 isolated，另一个仍提供公开代表报道。
- 影响：被隔离来源仍出现在热榜 sourceNames/participants，并参与人数和热度计算。文章详情撤回并不能实现注释承诺的“任何公开面都不出现”。本轮证明的是来源身份与参与信息残留，没有声称 isolated 原文正文直接泄漏。
- 证据：独立库构造两来源同一事件，隔离其一后执行 `republishSource` 和全新 `computeHotRanking`；该来源 publication 为 withdrawn，但 `loadHot()` 仍包含来源名。因此不是仅等待缓存过期即可解决。
- 建议：明确隔离、signal、暂停及历史信号的不同语义；在公开读与热度聚合边界一致执行，再重建衍生数据并处理旧缓存。不能只在 UI 隐藏头像。
- 缺失测试：隔离前后并重算的热榜计数/名称/头像，网站、v1/MCP 与事件/报告引用；至少保留另一个公开报道，避免整条 story 消失掩盖问题。

### R4 · P2 · 回执去重不包含供应商端点，切换服务可能错误复用旧结果

- 位置：`packages/backend/src/providers/llm.ts:191`、`:199`，逻辑键组成见 `packages/backend/src/providers/receipts.ts:71`。
- 原因：identity 包含模型、提示词和参数，但没有真正使用的 baseUrl/供应商配置身份；部分实际请求语义如 jsonMode 也没有完整进入 identity。
- 触发：使用相同 model/service、相同输入及提示词，把默认 LLM 从一个端点切换到另一个端点。
- 影响：新端点并未调用，返回旧端点已接收的响应；评测、模型切换与故障迁移可能获得错误来源的结果。
- 证据：在独立测试进程用两个 `.invalid` 假端点及进程内 fetch 桩，第二次更改 `LLM_BASE_URL`；总调用次数为 1，第二次 `reused=true` 且 receiptId 相同。无外网调用。
- 建议：使用规范化的非敏感 provider/endpoint identity 和有效请求语义；不要哈希或保存密钥来区分供应商。迁移旧回执的复用策略要明确。
- 缺失测试：同输入切端点/请求模式、同端点等价配置与既有缓存兼容。

### R5 · P2 · 后台运行时校验错误被映射为 500

- 位置：`packages/backend/src/admin/sources.ts:172`，`apps/api/src/routes/admin-auth.ts:59`。
- 原因：CreateSchema.parse 抛出 ZodError，但公共 adminHandler 仅把 statusCode=400 或 SyntaxError 映射成 invalid_request，ZodError 落入 internal_error。
- 影响：正常管理员输入错误被报告为服务故障，难以提供可纠正字段反馈，也污染故障告警。未发现由此绕过管理员权限的证据。
- 证据：测试进程配置合成 dev admin，通过真实 Fastify inject POST `/api/admin/sources`，payload `{name:""}`，得到 `500 / internal_error`。
- 建议：在已有输入边界统一映射可识别的校验错误为 400，输出经过限制的字段信息，保留真正内部异常的非敏感日志；前端保留输入并给出对应反馈。
- 缺失测试：合法登录 + CSRF 下的无效字段、冲突、内部异常，以及页面纠正重提交流程。

### R6 · P2 · 评测输出忽略数据目录，标准运行容器内会在调用完成后写盘失败

- 位置：`scripts/eval-relations.ts:178`、`:190`；selection 同类静态问题在 `scripts/eval-selection.ts:157`。部署上下文见 `Dockerfile:25` 与 `docker-compose.yml:13`。
- 原因：输出固定在 `REPO_ROOT/.data/eval`，不使用 `AIHOT_DATA_DIR`。现有运行容器由 node 用户运行，`/app` 为 root:root 755、`/data` 可写；COPY 子文件归 node 不使 `/app` 根目录可写。
- 影响：评测模型响应与回执可以已生成，但最终 mkdir/report 失败；真实评测可能付费后无输出报告。
- 证据：在配置临时 AIHOT_DATA_DIR 的 API 容器跑根测试，151 项中 149 通过，两项 relation-eval-runtime 因 `/app/.data/eval` EACCES 失败；仅为一次性容器在 `/app/.data` 挂载可写 tmpfs 后，同两项全部通过。未修改运行服务挂载、代码或系统目录权限。
- 建议：输出使用受控数据目录或明确 `--out`，在模型调用前检查输出可写；补“代码目录只读、数据目录可写”的运行测试。selection 仅静态确认路径同类，本轮未运行真实 selection 评测。

### R7 · P2 · MCP 检查脚本与行业工具名脱节，且工具错误不能可靠使验证失败

- 位置：`scripts/mcp-check.ts:13`、`:25`、`:27`；权威工具名见 `packages/contracts/src/mcp.ts:5`，默认前缀见 `industry/site.ts:27`。
- 原因：脚本硬编码 `aihot_*`，默认行业实际是 `myhot_*`；对正常返回的 MCP `isError` 只打印 ERROR，不设置失败退出或断言。
- 影响：改行业后会调用不存在的工具；若 SDK 将错误作为工具结果正常返回，脚本仍可能正常退出，形成“验证已通过”的假象。SDK 抛异常的情况则仍会失败，不能概括为所有错误都退出 0。
- 建议：复用 contracts 工具名/实际发现，明确哪些用例预期成功或预期无效参数，断言内容与退出码。不要把 listTools 成功当作工具业务路径成功。
- 证据级别：静态确认，本轮未执行该 SDK 检查脚本；运行镜像已裁掉对应开发依赖。没有宣称已完成所有 MCP 工具的真实验收。

### R8 · P3 · 畸形无关 Cookie 会把未登录后台查询变成 503

- 位置：`packages/backend/src/admin/auth.ts:51`、`:158`，`apps/api/src/routes/admin-auth.ts:51`。
- 原因：解析每个 Cookie 时直接 decodeURIComponent，非法编码抛错；sessionPrincipal 调用位于 adminHandler 的 try/catch 之外，落入全局错误处理。
- 证据：真实 Fastify inject GET `/api/admin/me`，Cookie 为 `unrelated=%`，返回 503，而不是正常未登录/无效 Cookie 处理。
- 影响：客户端本可忽略的 Cookie 造成后台请求失败；当前证据是带该 Cookie 的请求受影响，不是全站拒绝服务或认证绕过。
- 建议：局部容错解析无关/损坏 Cookie，保持登录与服务故障语义；补 malformed、过期及多 Cookie 测试。

## 4. 已有架构值得保留的部分

- Node 原生 TypeScript + npm workspaces；Fastify API、React Router web、独立 Worker；无需为“规范化”引入另一套框架或后端编译。
- 行业包与 contracts 已形成真实共享边界；web 经 HTTP，不直接访问数据库或模型。
- 材料身份/修订、分析输入版本、人工覆盖、来源参与模式和 publication 投影分别表达不同事实，优先修边界，不另建一套总状态机。
- 付费回执先保存响应、请求预算按 service 串行保护；关机等待与 unknown 恢复策略有意识处理成本风险。R1/R4 是已有机制的接缝问题，不是重建计费平台的理由。
- publication、入选快照/变更记录和统一 HTTP 策略使多出口一致性有基础；热榜信号缺口应在现有边界补齐。
- 原有测试覆盖幂等、修订、关机、请求取消、媒体、报告候选、信号和模型解析等重要路径；需要补跨模块恢复，不宜以增加测试数量代替真实断言。

## 5. 关键业务链路复核

### 5.1 材料、分析与事件

采集/ingest → `upsertMaterial` → `queueProcessing` → 提取/分析 → 归组 fact/story → 摘要/热度 → 发布。URL 与内容修订已有统一处理；旧版本结果需受修订保护。首次基线、显式回填、超过 48 小时历史材料有不同规则，不能统称为“新发现即今日新闻”。

分析含预筛、两次评分、结构化、理解/摘要等阶段，提示词在行业包；评分阈值与关系判断已有样本评测入口。不建议再加通用“质量合同”或盲目多模型重试，先修 R1/R4/R6 并用真实标注校准。

### 5.2 发布与多出口

文章投影负责公开资格、全文和延迟可见；网站、RSS、v1、MCP 与搜索等主要新闻出口复用 publication。热榜、可选排行榜和监控仍有专用读取模型，原 AGENTS 的“所有公开出口均来自 publication”过于绝对，已改为区分真实领域边界并要求权限贯穿衍生模型。

改成 isolated 会撤回文章投影，改 enabled 则不等于撤回所有历史公开内容。R3 证明热榜来源与计数未完整跟随隔离；批量 republish 或缩短缓存不是充分修复。

### 5.3 日报与排行榜

报告使用北京时间窗口、候选锁与公开时间，且有补跑和历史去重；变更截止边界需并发与迟到任务验证。排行榜有上游快照/解析、连通性与求解门禁、上一版回退等现有机制。算法模块已做结构与关键门禁检查，但本轮没有独立证明 Kemeny 求解正确性、上游实时可用性或所有价格映射。

### 5.4 后台、运营与 UI

后台存在 session/CSRF、审计、运行任务与回执处理；UI 复用 action 与统一客户端。R5/R8 属于边界错误处理，R1 属于“操作成功”与业务恢复脱节。前端 16 项通过仅证明现有自动断言，不表示所有后台表单已人工浏览器验收。

任务心跳、保留、备份、告警与看门狗已存在。不要继续添加监控平台代替修复断链；先确认当前运行记录能解释文章、回执、队列与公开结果。

## 7. 不是现成缺陷、但变更前必须确认的风险

1. 多 Worker：归组 localConcurrency=1 和文章行锁不等于事件图全局串行。当前 Compose 单 Worker，未用竞争测试证明现有实例已产生重复；扩容前按 B 类调查，而非直接宣布线上有并发事故。

### 10.2 逐项补充证据与校正

**R1：排除手工造 failed 状态导致的误判。** 本次捕获并执行 `registerContentJobs` 注册的实际 Worker 回调，以进程内模型桩模拟响应丢失。第一次调用进入真实 afterFailure，第二次重试遇到同一 unknown 回执，文章进入 failed。随后分别执行自动放行和真实管理员 release API；两种路径均未重入队。把创建时间推进到 sweep 窗口后仍不恢复。单独调用既有 queueProcessing 能成功入队，排除了队列本身不可用。回调在测试进程执行，未启动常驻 Worker，也未等待真实 30 分钟。

**R2：纠正信任假设。** `docs/sources.md:14` 和外部推送章节面向自有采集脚本；现有系统只有一个实例级 ingest 令牌，没有逐客户端、逐来源的权限模型。复核确认跨 kind 写入和暂停后写入可发生，也确认未知 sourceId 仍建为 external/isolated、无令牌无法调用。但这不能独立证明一个“有限权调用者”突破了已约定权限：若令牌仅由与管理员同等可信的自有脚本持有，跨来源写入可能属于原接口的宽权限设计。

当令牌交给只应写某些来源的外部集成时，此行为才构成明确的越权风险。新规范要求更窄的来源绑定，是目标约束；应在接入 Redfox 等有限权集成前落实。不能仅拿新写的规则反证旧设计必定存在 P1 漏洞。`enabled=false` 的既有实现主要暂停采集，未明确承诺撤销外部推送权限或终止所有在途处理，因此也撤回把这一行为单独认定为权限绕过的结论。确认契约后再决定限制已有入口还是分配更窄的凭证，避免破坏合法自有脚本。

**R3：排除绕过后台更新流程导致的误判。** 本次通过真实管理员 PATCH 修改 participation_mode，再执行 `registerPublicationJobs` 注册的实际重建回调。settings 进度为 done、reduced=1，文章投影为 withdrawn；新热榜仍保留隔离来源，参与人数从 2 到 2，web 读取和实际 `/api/v1/hot-topics` 响应均可见。后台没有另外清理信号的遗漏路径能够解释掉该结果。现有 `docs/sources.md` 已明确 isolated 不进任何公开页面，因此属于原有产品约束的真实偏差；按已证实的来源名与热度影响校准为 P2，不声称文章正文或私密数据外泄。

**R4：增加反例并收窄范围。** 同端点重复调用复用是正常对照；切到第二端点后仍返回第一端点的合成响应，只有设置新的 attemptTag 才实际调用第二端点。改变 LLM_JSON_MODE 也未改变回执身份，新 attemptTag 后实际请求才不带 response_format。`packages/backend/src/admin/content.ts:171` 的管理员重评估会设置 `admin:<requestId>`，这一路径不应被描述为必然错误复用。缺陷限于同一逻辑身份下发生了端点/有效请求配置变化、又没有显式新尝试标识的调用。上述结果不涉及真实供应商或计费。

**R5：排除开发管理员绕过带来的影响。** 本次使用独立测试库中的合成密码账号，通过真实 passwordLogin 生成会话；未启用 devAdmin。仅 name 无效、其余字段合法时返回 500/internal_error；纠正该字段后创建成功。认证与 CSRF 的拒绝对照正常。问题在输入错误分类，不是认证失效。未据此声称浏览器表单的每种无效输入都能绕过前端校验。

**R6：从单一测试失败扩展到两条真实脚本。** 单独执行 eval-relations 和 eval-selection，使用新合成 gold、本地 HTTP 模型桩、可写的 AIHOT_DATA_DIR，以及独立测试库。两者分别在完成 1 次、3 次桩调用后尝试创建仓库内 `.data/eval`，因运行容器 `/app` 不可写失败。selection 使用 `--no-import`。这确认了脚本输出路径缺陷，但不说明网站或日常 Worker 因此不可用；源码目录可写的本地开发环境不触发。首次审查的可写 tmpfs 对照仍是有效的既有证据，本轮没有为同一事实重复完整测试套件。

**R7：替换静态推断，区分协议错误与工具业务错误。** 在临时目录安装项目锁定的官方客户端 2.1.0，逐字复制原 mcp-check.ts 执行。连接本轮测试进程中的真实 API 后，列出 myhot 工具，随后因 `aihot_get_hot_topics` 不存在抛 ProtocolError，退出码 1。因此“默认配置下工具名不匹配却假成功”不成立。

另一个本地 MCP 对照服务器提供脚本期待的 aihot 工具名，并将所有业务调用返回 `isError:true`；相同原脚本打印 5 行 ERROR，最终退出码仍为 0。最后的 limit=99 是脚本原本的无效参数用例，不能单凭这一项 ERROR 判失败；本次连前面的正常参数用例也全部业务失败，才证明缺少成功断言。工具名脱节和不检查业务失败这两个问题均成立，但触发条件不同。早期手写协议探针缺少 Mcp-Name 头的 400 属于复核工具构造错误，未计入项目发现，最终以官方 SDK 结果为依据。

**R8：增加登录态和合法编码对照。** 除未登录请求外，正常已登录会话附加无关畸形 Cookie 也返回 503；合法编码的百分号不触发。影响仍限定为携带该坏 Cookie 的请求，不能据此声称全站拒绝服务或账号被接管。
