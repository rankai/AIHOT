## 1. 用户实际看到的流程

1. 描述需求或选Skill。缺少影响任务范围/价格的必要信息时，先简短询问；已有信息足够就直接准备报价。
2. 会话内显示一张费用卡：**“生成1张小红书封面，预计最多 X 积分。完成或停止后按实际执行结算。”** 默认仅显示任务、上限和“取消 / 确认开始”；明细可展开。
3. 可用积分不足X，显示“积分不足，还差 Y 积分”，不能确认或启动付费执行；输入、附件保留。并发任务占用的积分不算可用余额。
4. 确认后一次冻结X，连续完成本任务范围内的检索、分析、写作或生成，不在每次接口调用前弹出费用确认。
5. 需要选方案时，只展示编号选项和提交。若用户最初要“生成封面图”，生图已经计入这次上限，选好就继续生图，**不再出现第二张收费卡**。可选择“只保留方案”，未执行的生图部分不消费。
6. 完成显示“本次扣除 A 积分，已释放 B 积分”；主动停止也按相同规则处理。如果存在正在处理或结果未知的请求，先显示“已停止后续执行，费用核对中”，核对完再显示实扣与释放，不能提前承诺退款。

数字仅示例：上限300，最终应收180，释放120；不是正式售价。界面金额一律取服务端现有生效价目，不使用隔离测试价目。

### 任务边界

“任务”是用户本次确认的目标、材料、交付范围和规格，通常对应一个助手父任务；不是整段会话、单个模型调用或每个接口。问题补充、选择方案和同范围继续执行属于原任务；后续发送的独立修改、新增图片/视频或扩大数量是新请求。

用户原先只要设计方案，后来新增生图，是新任务，才重新报价。用户原先已要最终图片，选设计方案不是新增任务，不应再次收费确认。系统不能通过人为拆任务恢复逐接口打断。

## 4. 报价前怎样知道范围与上限

### 4.1 路由先确定任务范围，执行后不得随意扩大

目前部分模块在付费父模型开始后才确定，不能直接把所有可能Skill成本相加，或先扣创作费再补报价。本方案将**有界的任务识别前置到报价准备**：

- 明确的快捷任务、原任务修改引用及完整规格，能从已有能力绑定唯一确定时直接使用，不额外调用模型。
- 手选Skill仍可能含写作/改写/封面等多个能力；自动入口也可能需要语义判断。复用当前模型配置与目录说明，做至多一次短的路由/规格提取，只输出已注册任务能力或澄清问题，不执行Skill工具，不检索、不生图、不递归规划。
- 这次前置识别如果使用模型，会有供应商成本。**规划采用平台承担的受限报价准备成本，不扣会员积分**，必须走现有回执、用途预算、身份与成本记录；仅登录用户主动发送可触发，读页面/读目录不可触发。复用现有预算设施，增加明确的受控服务键（如`assistant.quote-preparation`），未配置时禁止调用；模型成本仍使用原pricingKey，另记`quote-preparation`用途。不另建模型供应商或Agent服务。现有预算按service/scope计数，不能仅写purpose就声称已有独立限额。
- 实施/真实验收前，平台报价准备预算须由管理员明确配置。未配置时不偷偷调用、不借会员创作费垫付；改为一次简短任务选择/补充。预算耗尽或识别不可靠也只澄清，不盲目以最贵任务报价。此限制属于实际运营前提，不能声称“未配置仍可自动语义识别”。
- 前置识别只能建议；后台检查候选属于当前用户/入口可用范围，参数符合已实现合同，再生成费用快照。模型不能返回自定义价格、权限或执行接口。报价准备入口在模型调用前复用现有用户限频与预算检查；按稳定准备命令/输入快照复用已记录结果，刷新、重复发送同一命令不重复购买路由。结果未知沿回执核对，不自动重试。

这不新增一套关键词路由，也不要求用户每次手工选模块。不上传完整大附件做费用预判，沿当前材料限制只提取报价必需信息；识别所得需求摘要要在费用卡可查看。平台前置调用费用独立记成本，不能混为用户任务实扣。

### 4.2 最小收费描述

在现有能力绑定中增量声明有限的任务收费描述（字段名在实施时沿现有schema确定），只允许：

- 对应已实现能力/交付合同；本次目标是方案、文章还是最终媒体。
- 允许的收费项目、最大计费次数及费用相关规格（如1张、1K、3:4或明确视频时长）；必要步骤和可放弃后续均计入本次目标的保守上限。
- 必要材料/范围约束，以及现有结果合同对应的结算依据。

描述只引用服务和价目匹配条件，金额仍由统一价目产生。无任意脚本、条件表达式、公式语言、流程图或执行顺序；也不重建Skill的写作流程。原外部SKILL.md是内容规程，不是收费授权来源。

**上限 = 各收费单位的最大数量 × 对应已批准单价/规格价之和。** 必须为每个可能的付费分支给出有限上界；正常重试是否另收费按既有价目/结算合同，不按HTTP次数机械加钱。没有完整定价或无法给出可信上限时，不启动该收费任务，明确需要补充的规格或后台配置。

例如文本创作按轮定价，内部多个文本模型调用仍只算该创作单位；视觉分析按一个报告定价，分四批看图不收四次会员价。供应商真实成本则逐次记录。用户只放弃生图时不消费图片单位，不能因此把已经交付的研究也说成免费。

## 5. 最小数据与执行改动

### 5.1 一笔总冻结＋收费项目明细

复用现有quote、charge、entry、operation结构，增加明确的任务组合定价/结算类型及快照。只新增一类必要的**任务收费项目分配记录**，关联总charge、授权项目/单位、原子分配的子run、计价快照、交付/回执依据及最终应收；具体采用一张功能关联表，不创建第二套余额或账本。

项目记录既支持尚未启动的预留槽位，也支持实际运行的原run与合法恢复引用；同一次逻辑收费单位只能分配一次，恢复不会新增收费单位。主创作项目也在其中，不能漏算或重复收取。现有单工具run links仍用于原根任务/恢复，禁止将其recovery标记冒充普通子任务。

新类型的授权查找（`chargeForRun/assertRunCredit`）、在途与交付聚合（`deliveryFacts`）、人工核对（`reconcileCreditCharge`）及会话未知围栏（`assertSessionReceiptsReviewed`）必须统一沿同一项目关联覆盖父任务、所有实际子run和恢复run；不能只替换冻结入口而让其余函数漏看子任务。旧类型继续沿旧links，无需再建一个独立授权服务。

### 5.2 用户确认必须原子化

同一事务核对用户、任务/材料快照、技能准入、报价期限、价格版本、服务健康、请求幂等键及可用余额；通过后创建总冻结、任务收费项目记录和父任务入队。任何一步失败，整体回滚；余额不足不产生可执行付费任务。

重复点击或响应丢失先读原命令结果，不能再冻结一笔。多窗口使用现有账户锁/成员准入锁和既定锁顺序，两个任务不能同时花同一份余额。报价准备与余额预览不冻结；确认瞬间必须重新核对。

### 5.3 执行时从任务已冻结额度分配，不再次扣钱包

子任务创建在原事务边界核对：属于该任务和激活范围、能力/价格规格匹配、剩余项目次数与金额足够、父任务未停止及generation有效；通过后占用任务内对应项目并入队。其付费请求仍经过现有预算/回执。

新模式的子任务**不创建独立钱包冻结、不再要求用户点击批准**，但并非无授权调用。执行器复用同一任务授权检查；通用执行路径不再只放行某个工具名。子完成仅保存该项目的结果/应收事实，不能触发整笔任务结算。后台必须核对授权关联，不能只信前端传来的taskId/chargeId。

会员单价在确认后按快照固定；常规改价不导致任务途中二次问价。报价确认前已改价则重新报价。供应商预算不足、服务关闭或其他安全限制仍可暂停执行，不意味着可以超额向用户扣费。

超出授权能力/数量/规格的提案不外发。属于用户新需求时保留已有成果、结束或明确取消旧范围后准备新任务报价；模型自己扩大范围不是用户同意，不能默认购买或自动拆出新付费任务。

## 6. 结算、停止与异常恢复

“实际结算”指**按首次冻结的会员价目，对实际达到收费条件的项目结算**，不是直接把供应商成本折成人民币或按token重新定价；本方案不修改会员单价、原工具交付规则或供应商定价。

| 情况 | 行为 |
| --- | --- |
| 正常完成 | 每项依据原有合法交付事实判断应收，求和A≤总冻结X；整单一次consume A、release X−A |
| 用户只保留方案 | 若原任务含生图，明确放弃未执行图片项目，汇总其余应收并释放差额 |
| 外发前主动停止 | 先停止父子派发，确认无在途；若所有项目未执行应收为0，全部解冻 |
| 部分完成后停止 | 确认所有在途状态后，已达到收费条件的项目计入，未执行/已明确不应收费项目不计入，整单结算 |
| 失败、部分交付 | 沿原项目交付规则；供应商成功但保存失败不直接退款或重发，先恢复保存/核对。不能一律成功全扣或一律失败全退 |
| 有pending/unknown | 停止后续派发，整单转review，**暂保留这笔总冻结**；显示核对中，解决全部未定事实后一次结算。首版不做分批扣退 |
| 无法自动消除unknown | 进入原后台人工核对，按证据记录原因与审计；pending仍须等结果，unknown不能被设计为永远禁止核对。人工终结不改写历史回执 |

新任务模式下，停止入口意味着“终止本次任务并结算”，不是无限期暂停占款。先沿现有generation/父子状态停止派发，再由根任务协调汇总，不继续逐run尝试结算总冻结。事务与在途请求有竞态时，以已落库的请求/回执事实核对，不能假定点击停止等于远端取消成功。

已结算/释放的任务不能恢复外发。用户之后继续制作，复用已保存方案/材料/可用研究证据，针对剩余工作发起新任务并报价；不重复购买已可复用结果。等待用户选择/补充不是主动停止，仍在原任务内。刷新、掉线、Worker重启、已发请求核对属于原任务恢复，不新增冻结、不重新发未知请求。

未知状态延后整单结算是为复用已有`reserved/review → settled/released`及一次最终流水不变量，避免首版引入分批账本。余额页应区分“可用”和“核对中冻结”，不能显示已退回。必须有现有后台可操作的核对入口，不能只留一条无法处理的提示。

## 7. UI、现有授权、历史与队列

- 新任务只展示一张总费用卡，默认任务目标、预计上限、确认/取消；详情中可看包含项目、范围、余额和按实际结算说明。删除本任务内重复的“单独收费/另行批准”，子步骤只显示执行状态。
- 初始余额不足直接禁用确认并提示差额；报价过期/确认前价格变动才显示更新报价。刷新页面恢复同一报价/冻结任务，不把确认卡重复当新请求。
- 图片/视频的张数、规格、时长等影响费用的选项在初始报价前确认；后续方案选择不改变这些规格，不出现第二次付款按钮。
- 新任务模式先采用明确的一次任务确认。旧“额度内自动”只覆盖旧范围，**不得拿旧会话授权替代新总冻结确认**；新模式输入区不继续提供会误导用户的旧自动模式选项，保留简单的费用规则说明。新任务跨任务自动授权不在首版范围内。
- 队列中的未执行需求不提前占款；轮到时基于当前上下文准备总报价，用户确认后才冻结并执行。队列等待不算执行，取消排队无费用。已经确认并冻结的同一任务等待选择或恢复不重新报价。
- 用明确的组合报价/charge类型区分新旧。旧已确认/在途任务继续原授权、单项结算和恢复语义，历史账目不变；旧未确认报价若因包版本或计费合同升级无法通过原快照校验，保留需求与材料并明确重新报价，不冻结、不扣费、不把旧同意升级为总任务授权。旧队列保留既有已确认语义；尚未确认且范围已变化的需求同样重新报价。新类型覆盖新请求；绑定或合同含义变化时发布新版本，不覆盖旧包/旧快照。旧执行兼容待旧任务终结后停止接收，历史只读保留。
- 后台停用Skill继续阻止新任务，已确认任务沿冻结范围执行；未确认报价提交时再查准入。历史作品不依赖Skill当前启用状态。

## 8. 成本中心复用与可扩展性

会员积分收入与供应商成本是两套事实，必须分开：
